# DB & AI - 개발 환경, 인증, 서버와 배포

## 💡 Q&A - ChatPromptTemplate 자료형
- `from_messages()`는 여러 메시지를 순서대로 전달하기 위해 `List`를 사용한다.
- 각 메시지는 `(role, content)` 두 값의 쌍으로 표현할 수 있어 `Tuple`을 사용한다.
- 예: `("system", "내용")`, `("user", "내용")`
- 이는 Python의 필수 규칙이 아니라 LangChain이 지원하는 입력 형식(API 규격)이다.

## Session vs Token 로그인
- **Session**은 로그인 상태를 서버에 저장하고 Session ID로 사용자를 식별한다.
- **Token**은 로그인 후 Token을 발급하고 이후 요청마다 이를 제시하여 인증한다.
- Session은 서버에서 통제하기 쉽지만 세션 저장·공유가 필요하고, Token은 API·분산 환경에 유리하다.
- `JWT(JSON Web Token)`는 Token 방식에서 사용할 수 있는 대표적인 토큰 형식 중 하나이다.

## Hash
- **Hash**는 입력 데이터를 일정한 길이의 값으로 변환하는 단방향 함수이다.
- 같은 입력은 같은 결과를 만들며, 원본을 역으로 복원하기 어렵게 설계된다.
- 비밀번호는 평문 대신 `salt + Argon2/bcrypt` 같은 비밀번호 해싱 방식으로 저장한다.
- 비밀번호 보호뿐 아니라 파일 무결성 검사, Git 등 다양한 곳에서 활용된다.

## Server & Cloud
- **Server**는 Client의 요청을 받아 데이터나 기능을 제공하는 프로그램/컴퓨터이다.
- 내 PC도 서버가 될 수 있지만 실제 서비스는 24시간 운영을 위해 Cloud Server를 많이 활용한다.
- AWS·Azure·Google Cloud는 서버·DB·스토리지 등의 자원을 제공하는 **Cloud Provider**이다.
- GPU·TPU는 AI 연산을 빠르게 처리하는 계산 장치이며, TPU는 Google이 개발한 AI 가속기이다.

## Region
- **Region**은 Cloud Provider가 서비스를 운영하기 위해 구분해 놓은 물리적인 지리적 영역이다.
- 예: 한국(서울), 일본(도쿄), 미국 등의 Region 중 서비스를 운영할 위치를 선택한다.
- 사용자와 가까운 Region은 일반적으로 네트워크 지연시간(Latency)을 줄이는 데 유리하다.
- 데이터 규제, 비용, 서비스 제공 여부, 장애 대비 등을 고려하여 Region을 선택한다.
- 💡 `Cloud = 건물 체인 / Region = 어느 지역의 지점을 사용할 것인가`로 생각하면 쉽다.

## Docker
- **Docker**는 애플리케이션과 필요한 실행 환경을 `Container`로 묶어 실행하는 도구이다.
- 개발 PC와 서버의 환경 차이로 발생하는 **"내 컴퓨터에서는 되는데?"** 문제를 줄여준다.
- `Dockerfile → Image → Container 실행`의 흐름으로 이해할 수 있다.
- AX/AI 개발에서는 AI 앱·DB 등의 개발 환경을 재현하고 서버에 배포할 때 유용하다.

---

## Docker 직접 배포
- 애플리케이션을 `Docker Image`로 만들고 Cloud Server에서 `Container`로 직접 실행할 수 있다.
- 서버 생성 → Docker 설치 → Image 전달/Registry → Container 실행 → 네트워크·환경변수 설정 등을 관리한다.
- 실행 환경을 세밀하게 통제할 수 있지만 서버·보안·HTTPS·로그·업데이트 등을 직접 관리해야 한다.
- 💡 Docker 자체는 배포 서비스가 아니라 **동일한 실행 환경을 만들어주는 기술**이다.

## 간이 배포
- 학습·프로토타입에서는 Render, Vercel, Streamlit Cloud 등의 관리형 서비스를 활용할 수 있다.
- GitHub Repository를 연결하면 Build와 배포 과정의 상당 부분을 플랫폼이 대신 처리한다.
- 서버 관리 부담이 적어 **MVP·포트폴리오·데모**를 빠르게 공개하는 데 유리하다.
- ⚠️ 대신 서버 설정, 확장성, 비용 구조 등에 제약이 있을 수 있다.

---

## Beta Test
- **Beta Test**는 정식 출시 전 실제 사용자에게 서비스를 제공하여 문제와 사용성을 검증하는 단계이다.
- 내부 중심의 Alpha Test와 달리 제한된 실제 사용자를 대상으로 진행하는 경우가 많다.
- 버그뿐 아니라 UX, 기능, 응답속도와 실제 사용자의 피드백 등을 확인한다.
- AI 서비스에서는 **답변 품질과 예상하지 못한 사용자 입력**도 중요한 검증 대상이다.

## Load Test
- **부하 테스트**는 많은 사용자가 동시에 요청했을 때 서버가 안정적으로 처리할 수 있는지 확인하는 테스트이다.
- Script로 가상의 사용자와 요청을 만들어 실제 트래픽과 비슷한 상황을 재현한다.
- 응답시간, 처리량(Throughput), 오류율, CPU·Memory 등을 확인하여 병목을 찾는다.
- 대표적인 도구로 `Locust`, `k6`, `JMeter` 등이 있다.

## 오늘의 연결

```text
사용자
  ↓
로그인 ── Session / Token
  ↓
Server ─────────────→ DB
  │                    └─ Password Hash
  ├──→ AI / LLM
  │
  └── 애플리케이션
          ↓
       Docker
          ↓
   Cloud Provider
   AWS / Azure / GCP
          ↓
       Region 선택
          ↓
      서비스 운영
```

### 개발 → 배포 흐름

```text
개발
→ 테스트
→ 간이 배포 / MVP
→ Beta Test
→ Load Test
→ Docker + Cloud 운영 배포
→ 정식 서비스
```
