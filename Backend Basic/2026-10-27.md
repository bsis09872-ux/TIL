## 2. REVIEW — 튜터님의 백엔드 기초 강의

### A. 동기·비동기 처리와 백그라운드 작업

**동기(Synchronous)**

- 앞선 작업이 완료될 때까지 기다리는 방식
- 작업 처리 순서가 중요한 경우에 사용

**비동기(Asynchronous)**

- 네트워크·파일 입출력 등 대기 시간이 발생하는 작업에 적합
- 대기하는 동안 다른 요청을 처리할 수 있음

**백그라운드 작업(Background Task)**

- 요청 처리와 분리하여 별도의 실행 흐름에서 작업
- 오래 걸리는 작업은 별도 작업자나 프로세스를 고려

**핵심:** `async def`를 선언했다고 작업이 자동으로 백그라운드에서 실행되는 것은 아니다.

### C. REST API와 HTTP 요청

REST(Representational State Transfer)는 웹 자원을 식별하고 HTTP 메서드를 활용하는 아키텍처 스타일이다.

| 구성 요소    | 역할                     |
| ------------ | ------------------------ |
| Method       | 요청 작업의 종류         |
| URL          | 요청할 자원의 위치       |
| Header       | 인증 정보·데이터 형식 등 |
| Body         | 생성·수정할 데이터       |
| Query String | 검색·정렬 등 추가 조건   |

### D. HTTP Method와 멱등성

멱등성(Idempotency)은 동일한 요청을 여러 번 실행하더라도 의도된 최종 효과가 한 번 실행했을 때와 같은 성질이다.

| 메서드   | 역할      | 멱등성           |
| -------- | --------- | ---------------- |
| `GET`    | 조회      | O                |
| `POST`   | 생성·처리 | 일반적으로 X     |
| `PUT`    | 전체 교체 | O                |
| `PATCH`  | 부분 수정 | 구현에 따라 다름 |
| `DELETE` | 삭제      | O                |

### C. POST — 도서 등록 API

튜터 코드:

```python
@app.post("/books", status_code=status.HTTP_201_CREATED)
async def create_book(
    title: str = Body(..., description="등록할 책의 이름"),
    author: str = Body(..., description="등록할 책의 저자")
):
    global id_generator
    logger.info(f"신규 도서 등록: 제목 = {title}, 저자 = {author}")

    try:
        new_book = Book.create(id_generator, title, author, 'AVAILABLE')

        logger.info(f"신규 도서 등록 성공: 제목 = {title}, 저자 = {author}")

        id_generator += 1
        return new_book.to_dict()
    except ValueError as err:

        logger.error(f"신규 도서 등록 실패: {str(err)}")

        raise HTTPException(
            status_code=status.HTTP_400_BAD_REQUEST,
            detail=str(err)
        )
```

**처리 흐름**

1. `POST /books` 요청 수신
2. `Body(...)`로 필수 데이터 수신
3. `Book.create()`에서 데이터 검증 및 객체 생성
4. 성공 시 도서 객체를 딕셔너리로 변환
5. 실패 시 `400 Bad Request` 반환

**[코드 확인 사항]**

현재 저장소의 `create_book()`은 `new_book` 객체를 생성하고 반환하지만, 선언된 `in_memory_db`에 저장하지 않는다.

따라서 해당 코드만으로는 등록된 도서가 실제 목록 저장소에 누적되지 않는다.

| 코드                 | 의미                    |
| -------------------- | ----------------------- |

**중요한 차이**

Python 함수에서는 `search_keyword`를 사용하지만, 브라우저에서는 `keyword`라는 이름으로 값을 전달한다.

```text
/books?keyword=python
```

### E. Optional과 기본값

```python
search_keyword: Optional[str] = Query(None)
```

- `Optional[str]`: 허용하는 타입
- `None`: 생략 시 기본값
- `Query()`: 요청 매개변수의 검증 조건 설정

`Optional`만 선언한다고 자동으로 생략 가능한 매개변수가 되는 것은 아니다.

### C. Pydantic — BaseModel과 Field

**파일:** `chapter02-1/src/book/presentation/schemas.py`

튜터 코드:

```python
class BookCreate(BaseModel):
    title: str = Field(..., min_length=2, max_length=100, description="책 제목")
    author: str = Field(..., min_length=2, max_length=50, description="저자")
    price: Optional[int] = Field(None, description="책 가격", gt=0)
```

**필드별 검증**

| 필드     | 자료형          | 검증 조건            |
| -------- | --------------- | -------------------- |
| `title`  | `str`           | 필수, 2~100자        |
| `author` | `str`           | 필수, 2~50자         |
| `price`  | `Optional[int]` | 선택, 입력 시 0 초과 |

**Field 옵션**

- `...`: 필수값
- `None`: 기본값
- `min_length`: 최소 문자열 길이
- `max_length`: 최대 문자열 길이
- `gt`: 지정한 값 초과
- `description`: 필드 설명

### D. field_validator — 필드별 검증

튜터 코드:

```python
@field_validator("title", "author")
@classmethod
def trim_and_validate(cls, value: str) -> str:
    trimed_text = value.strip()
    if len(trimed_text) < 2:
        raise ValueError("공백없이 2자 이상 입력하세요.")

    return trimed_text
```

**처리 흐름**

1. `title` 또는 `author` 입력
2. Pydantic의 기본 검증 수행
3. `trim_and_validate()` 실행
4. `strip()`으로 양쪽 공백 제거
5. 제거 후 길이가 2글자 미만이면 `ValueError`
6. 검증을 통과한 문자열 반환

**핵심**

`@field_validator("title", "author")`는 하나의 함수로 두 필드를 검증한다.

`mode`를 생략하면 기본값은 `after`이다.

### E. model_validator — 모델 전체 검증

튜터 코드:

```python
@model_validator(mode="before")
def before_validate(self) -> Self:
    logger.info(f"[BEFORE]: {self}")

    return self

@model_validator(mode="after")
def after_validate(self) -> Self:
    logger.info(f"[AFTER]: {self}")

    return self
```

**mode의 차이**

| 모드     | 시점           | 주요 용도                  |
| -------- | -------------- | -------------------------- |
| `before` | 필드 검증 이전 | 원시 입력 데이터 확인·가공 |
| `after`  | 모델 검증 이후 | 필드 간 관계 검증·후처리   |

**[코드 확인 사항]**

튜터님의 `before_validate()`는 매개변수 이름을 `self`로 작성했지만, 일반적인 Pydantic v2의 `mode="before"` 검증 함수에는 모델 인스턴스가 아니라 원시 입력 데이터가 전달된다.

따라서 이름이 `self`라고 해서 검증 완료된 모델 객체를 의미하지 않는다.

이 코드는 검증 전후 입력과 모델의 차이를 확인하는 학습 사례로 이해하되, 실제 구현할 때는 각 모드의 입력 형태에 맞춰 작성해야 한다.

### F. Field 검증과 Validator의 차이

| 구분              | 역할                                   |
| ----------------- | -------------------------------------- |
| `Field`           | 기본적인 타입·길이·범위·필수 여부 검증 |
| `field_validator` | 특정 필드에 대한 사용자 정의 검증      |
| `model_validator` | 모델 전체 또는 필드 간 관계 검증       |

**예시**

- 제목 길이가 2자 이상인가? → `Field`
- 제목의 공백을 제거하고 다시 확인하는가? → `field_validator`
- 시작일이 종료일보다 빠른가? → `model_validator`

## 5. LECTURE NOTE — 2장 2강: 요청·응답 모델과 직렬화

### A. Request Model — BookCreate

튜터 코드:

```python
@app.post("/books", status_code=status.HTTP_201_CREATED)
async def create_book(payload: BookCreate):
    logger.info(f"BookCreate:{payload}")
    book = payload.model_dump(exclude_unset=True)
    logger.info(f"book={book}, type: {type(book)}, 제목: {book['title']}")

    books.append({
        "title": payload.title,
        "author": payload.author,
        "price": payload.price
    })
```

**처리 흐름**

1. 클라이언트가 JSON 요청 바디 전달
2. `BookCreate` 모델이 입력값 검증
3. `payload` 객체 생성
4. `model_dump(exclude_unset=True)` 실행
5. `books` 리스트에 도서 데이터 추가

### B. Serialization — model_dump()

```python
book = payload.model_dump(exclude_unset=True)
```

- `model_dump()`: Pydantic 모델을 Python 딕셔너리로 변환
- `exclude_unset=True`: 명시적으로 입력하지 않은 필드 제외

**주의할 점**

실제 튜터 코드에서는 `model_dump(exclude_unset=True)`로 만든 `book` 딕셔너리를 로그에 사용한다.

그러나 `books.append()`에서는 `book`을 사용하지 않고 `payload.title`, `payload.author`, `payload.price`를 직접 읽어 새 딕셔너리를 만든다.

따라서 `model_dump()`의 출력 결과와 리스트에 저장하는 내용이 정확히 동일한 흐름은 아니다.

### C. Response Model — BookResponse

튜터 코드:

```python
class BookResponse(BaseModel):
    title: str
    author: str
    price: Optional[int] = None
```

**Request와 Response 구분**

| 구분   | BookCreate       | BookResponse     |
| ------ | ---------------- | ---------------- |
| 역할   | 요청 데이터 검증 | 응답 데이터 형식 |
| title  | 필수, 길이 검증  | 문자열           |
| author | 필수, 길이 검증  | 문자열           |

### D. APIResponse — Generic 응답 모델

튜터 코드:

```python
T = TypeVar('T')

class APIResponse(BaseModel, Generic[T]):
    success: bool = Field(..., description="처리 성공 여부")
    error: Optional[str] = Field(None, description="실패 오류 메세지")
    data: Optional[T] = Field(None, description="성공시 응답 데이터")
```

**역할**

- `success`: 처리 성공 여부
- `error`: 실패 시 오류 메시지
- `data`: 실제 응답 데이터
- `Generic[T]`: 응답 데이터 타입을 유연하게 지정

### E. GET — 공통 응답 모델 사용

튜터 코드:

```python
@app.get("/books", response_model=APIResponse[List[BookResponse]])
async def get_book_all():
    return APIResponse(success=True, data=books)
```

**구성 분석**

```python
APIResponse[List[BookResponse]]
```

- `BookResponse`: 도서 한 권의 응답 구조
- `List[BookResponse]`: 여러 도서의 목록
- `APIResponse[...]`: 성공 여부·오류·데이터를 담는 공통 응답 구조

즉, 여러 도서 데이터를 공통 응답 모델에 담아 반환한다.

### F. 응답 구조 예시

```json
{
  "success": true,
  "error": null,
  "data": [
    {
      "title": "Python API",
      "author": "Tutor",
      "price": 20000
    }
  ]
}
```

위 JSON은 모델 구조를 이해하기 위한 설명용 예시이며, 저장소에 고정된 실제 응답 데이터는 아니다.

### G. 함수 매개변수의 `*`

튜터 코드에 주석으로 기록된 예제:

```python

#     # a, b, c -> 위치 매개변수
```

- `a`, `b`, `c`: 위치 인자로 전달 가능

## 6. TROUBLESHOOTING & LEARNING

### A. Query String과 Optional의 관계

**헷갈린 점**

`Optional[str]`을 선언하면 자동으로 선택적 매개변수가 되는가?

**해결**

- `Optional[str]`: `str` 또는 `None` 허용
- `Query(None)`: 매개변수 생략 허용
- `alias="keyword"`: 실제 URL에서 사용할 이름 지정

### B. Field와 Validator의 차이

**헷갈린 점**

`Field`에서도 길이를 검사하는데 `field_validator`가 필요한 이유는 무엇인가?

**해결**

- `Field`: 기본적인 제약 설정
- `field_validator`: 추가적인 검증·변환
- `model_validator`: 모델 전체 검증

튜터 코드에서는 `Field`의 길이 제한 외에 `strip()`으로 공백 제거 후 다시 검사하는 방식을 확인했다.

### C. before와 after

**헷갈린 점**

검증 전후 처리의 정확한 차이

**해결**

- `before`: 기본 검증 이전의 원시 입력
- `after`: 기본 검증 이후의 값 또는 모델

특히 `model_validator(mode="before")`에서 검증 완료된 모델이 전달된다고 생각하지 않도록 주의한다.

### D. model_dump와 실제 저장 데이터

**새롭게 확인한 점**

튜터 코드에서 `model_dump(exclude_unset=True)` 결과를 로그에 출력하지만, 실제 리스트 저장은 별도의 딕셔너리 생성 코드가 담당한다.

따라서 직렬화 결과를 확인하는 작업과 데이터를 저장하는 작업은 구분해야 한다.

### E. 요청 모델과 응답 모델

**새롭게 이해한 점**

입력값을 검증하는 `BookCreate`와 외부에 전달할 `BookResponse`는 역할이 다르다.

API의 입력과 출력을 별도 모델로 관리하면 각 방향의 데이터 계약을 명확히 정의할 수 있다.

## 7. REVIEW

### A. 오늘 새롭게 이해한 점

1. FastAPI의 라우터는 HTTP 요청을 받는 진입점이다.
2. 도메인 모델은 비즈니스 규칙을 관리한다.
3. Query String은 조회 조건을 전달한다.
4. `alias`로 Python 변수명과 외부 요청 매개변수 이름을 구분할 수 있다.
5. Pydantic `BaseModel`은 요청·응답 데이터 구조를 정의한다.
6. `field_validator`와 `model_validator`는 검증 범위가 다르다.
7. `model_dump()`는 Pydantic 모델을 딕셔너리로 변환한다.
8. `Generic[T]`를 이용하면 여러 응답 데이터 타입에 공통 형식을 적용할 수 있다.
