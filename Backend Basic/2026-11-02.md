## 1. 비동기 DB 연결 구성

| 구성 요소 | 역할 |
|---|---|
| `asyncpg` | PostgreSQL 비동기 드라이버 |
| `create_async_engine` | DB 연결 + **커넥션 풀** 관리 (연결을 미리 만들어 두고 재사용) |
| `async_sessionmaker` | 요청마다 쓸 `AsyncSession`을 찍어 내는 공장 |
| `.env` | 개발 환경과 배포 환경의 DB 접속 정보를 분리 |

```python
AsyncSessionLocal = async_sessionmaker(
    bind=engine, class_=AsyncSession,
    autoflush=False,          # SQL 전송 시점을 직접 통제
    expire_on_commit=False,   # 비동기에서는 필수 (동기식이면 True 가능)
)
```

- **동기와 비동기의 차이:** 동기는 작업이 끝날 때까지 다음 처리가 대기한다(블로킹). 비동기는 DB나 네트워크처럼 **대기 시간이 긴 작업**에서 유리하지만, 항상 더 빠른 것은 아니다.
- **파일 처리:** 파일 전체를 메모리에 올리면 부담이 크다. **청크 단위로 스트리밍**하면 부담이 줄어든다.

## 2. 세션과 트랜잭션

- **세션** = 앱과 DB 사이의 작업 공간(장바구니). **요청 1개 = 세션 1개**
- 세션이 하는 일: 변경 추적(Dirty Checking), 트랜잭션 관리, 1차 캐시(Identity Map)
- **SQLAlchemy 2.0에는 auto commit이 없다.** 반드시 직접 `commit()`해야 영구 반영된다.
- 여러 작업을 하나의 트랜잭션으로 묶고, 실패하면 `rollback()`으로 전부 취소한다. 이것이 **원자성**이다.
- **flush**는 SQL을 DB로 보내는 것(아직 확정 아님), **commit**은 영구 확정이다.
- **`expire_on_commit=False`인 이유:** True면 commit 후 속성에 접근할 때 몰래 재조회가 일어난다. 비동기에서는 `await`할 수 없는 지점이라 `MissingGreenlet` 에러가 난다. 그래서 DB가 생성한 값은 `await session.refresh()`로 명시적으로 가져온다.

> **비동기 핵심 원칙:** "몰래, 자동으로 일어나는 DB 조회"가 있으면 안 된다. 모든 DB 작업은 `await`와 함께 명시적으로 한다.

### `await`를 붙이는 규칙

`await`는 **`async def`로 정의된 함수에만** 붙인다. 판단 기준은 **"DB에 갔다 와야 하면 await"**다.

| `await` 필요 없음 (메모리 작업) | `await` 필요 (DB 통신) |
|---|---|
| `add()`, `add_all()`, `expunge()` | `get()`, `execute()`, `scalar(s)()`, `commit()`, `rollback()`, `refresh()`, `flush()`, **`delete()`** |

- `await`를 **빼먹으면** 에러 없이 실행되지 않고 `coroutine was never awaited` 경고만 뜬다. 찾기 어려워서 더 위험하다.
- 일반 함수에 `await`를 **붙이면** 즉시 `TypeError`가 난다.

## 3. 서버 생명주기와 의존성 주입

### `lifespan`과 `yield`

```python
@asynccontextmanager
async def lifespan(app):
    init_models()                                   # ⬆ 서버 시작 시 1번
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    yield                                           # ⏸ 서버 동작 중
    await close_db()                                # ⬇ 서버 종료 시 1번
```

- `yield`를 쓰면 **시작 코드와 정리 코드를 한 함수에 짝지어** 둘 수 있다. 에러가 나도 정리 코드가 실행된다.
- `get_db()`도 같은 구조다. 세션을 만들고, `yield`로 빌려주고, 요청이 끝나면 정리한다.

### `Depends` = 의존성 주입

- `Depends(X)`는 **"X를 실행한 결과를 이 매개변수에 넣어 줘"**라는 뜻이다.
- 함수가 필요한 것을 직접 만들지 않고 **외부(FastAPI)가 만들어서 넣어 준다.**
- 수업 프로젝트에서는 세션 → Repository → Service → 라우터 순서로 **연쇄 주입**된다. 장점은 중복 제거, 관심사 분리, 테스트할 때 교체가 쉽다는 것이다.

## 4. ORM 모델 정의

### 모델 정의 ≠ 테이블 생성

1. `class X(Base)` 코드가 **import되어 실행돼야** `Base.metadata`(명부)에 등록된다.
2. `create_all`은 **명부에 등록된 테이블만** 만든다.
3. 그래서 `init_models()`에서 모델 파일을 import한다. 순환 import를 피하려고 함수 안에서 import한다.
4. `create_all`은 **기존 테이블을 수정하지 않는다.** 모델을 바꿨으면 테이블을 지우고 다시 생성해야 한다(실무에서는 Alembic 사용).

### `Mapped`와 `mapped_column`

| 자리 | 넣는 것 | 예시 |
|---|---|---|
| `Mapped[...]` | **파이썬 타입** | `bool`, `str`, `int`, `datetime`, `str \| None` |
| `mapped_column(...)` | **DB 컬럼 타입 + 제약** | `Boolean`, `String(40)`, `Text`, `BigInteger`, PK, index |

- `| None`이 없으면 자동으로 NOT NULL이 된다.
- `Boolean`처럼 단순한 타입은 생략할 수 있다. `String(n)`처럼 세부 설정이 필요한 타입은 직접 적는다.
- `ForeignKey`를 쓰면 컬럼 타입을 생략해도 참조 대상의 타입을 따라간다.

### 시간 기준

- **UTC+0으로 저장하고, 표시할 때만 한국 시간(UTC+9)으로 변환**한다. `DateTime(timezone=True)`를 쓴다.
- 기본값은 **함수로** 넘긴다: `default=lambda: datetime.now(timezone.utc)`
- 반복되는 `created_at`, `modified_at`, `deleted_at`은 Mixin 클래스로 공통화할 수 있다.

## 5. 게시판 실습: Board 1 : N Post

```
boards (게시판 설정, PK: "qna" 같은 문자열)  1 ─── N  posts (게시글, PK: BigInteger 자동 증가)
                                                       └─ board_id → boards.id (FK)
```

- 레코드 1개 = 게시판 1개. 권한(쓰기·댓글은 회원), 활성 여부 같은 **설정**을 담는다.
- FK는 **N쪽(게시글)**에 둔다.
- 게시글 PK는 데이터가 계속 쌓이므로 범위가 큰 `BigInteger`를 쓴다. 제목은 `String(n)`, 본문은 `Text`로 한다.

### `ondelete`: 부모가 삭제되면?

| 옵션 | 동작 |
|---|---|
| `CASCADE` | 자식도 함께 삭제 |
| `RESTRICT` | 부모 삭제를 막음 |
| `SET NULL` | FK를 NULL로 바꾸고 자식은 남김 |

게시판은 다른 기능과 엮여 있으므로 함부로 삭제하지 않는다. 소프트 삭제(`is_active`, `deleted_at`)를 고려한다.

### 인덱스

- 장점은 검색, 조인, 정렬이 빨라지는 것이다.
- 단점은 저장 공간이 늘고 삽입·수정·삭제가 느려지는 것이다.
- **자주 검색하는 컬럼에만** 단다. `board_id`, `category`는 적합하고, 긴 본문(`content`)은 적합하지 않다.

## 6. 비동기 CRUD 흐름

| 작업 | 흐름 |
|---|---|
| 생성 | `Model(...)` → `session.add()` → `await commit()` → `await refresh()` |
| 조회 | PK면 `await session.get()`, 조건 조회면 `select()` + `scalar(s)` |
| 수정 | 조회 → 속성 변경(**Dirty Checking**) → `await commit()` |
| 삭제 | 조회 → `await session.delete()` → `await commit()` |

- **1차 캐시:** 같은 세션 안에서 이미 조회한 객체는 DB 대신 메모리에서 꺼낸다. 세션은 요청마다 새로 만들어지므로 **요청이 바뀌면 캐시도 새로 시작**된다.
- **Dirty Checking은 변경을 감지만 한다.** 실제 UPDATE는 `commit()` 때 실행된다.
- **`Post(...)`의 출처:** 모델 파일에서 import한 ORM 클래스다. `Base`가 `Mapped` 필드를 키워드 인자로 받는 생성자를 자동으로 만들어 준다.
- `Post(board_config=board)`처럼 관계 객체를 넣으면 commit할 때 `board_id`가 자동으로 채워진다.

## 7. 관계 매핑

### 단방향 vs 양방향 (반과 학생 비유)

- **단방향:** 학생 이름표에만 "1반"이 적혀 있다. `post.board_config`만 가능하다.
- **양방향:** 반에도 출석부가 있다. `board.posts`도 가능하다.
- DB의 FK 컬럼은 여전히 자식 쪽에만 있다. 양방향은 **파이썬 코드에서의 탐색 방향** 문제다.

### `back_populates`

```python
# Board
posts: Mapped[list["Post"]] = relationship(back_populates="board_config")
# Post
board_config: Mapped["Board"] = relationship(back_populates="posts")
```

- 양쪽에 **상대방의 속성 이름**을 적어 한 쌍으로 연결한다.
- 한쪽만 바꿔도 반대쪽 메모리 값이 자동으로 동기화된다. 이름이 정확히 일치해야 한다.

### N:M (게시글 ↔ 태그)

- FK 2개로 이루어진 **중간 테이블(Association Table)**로 연결한다. `relationship(secondary=중간테이블)`을 쓴다.
- `post.tags.append(tag)`를 하면 중간 테이블에 INSERT가 실행된다.
- `post.tags.clear()`를 하면 **연결만** 삭제된다. Tag 자체는 남는다.

## 8. 로딩 전략과 N+1 문제

> **양방향 매핑**은 "무엇이 연결되어 있나"를, **로딩 전략**은 "연결된 데이터를 언제, 어떻게 가져오나"를 정한다. 서로 다른 개념이다.

| 전략 | 방식 | 적합한 관계 |
|---|---|---|
| `lazy="select"` (기본값) | 속성에 접근할 때마다 쿼리 | ❌ 비동기에서 `MissingGreenlet`, N+1 문제의 원인 |
| `selectin` / `selectinload` | 부모를 조회한 뒤 `WHERE id IN (...)`으로 자식을 **한 번에** 조회 (쿼리 2번) | **1:N, N:M 목록** |
| `joined` / `joinedload` | JOIN으로 쿼리 1번 | **N:1, 1:1 단건** |

- **N+1 문제:** 부모 N개를 조회한 뒤 자식을 하나씩 조회하면 쿼리가 N+1번 실행된다.
- 1:N에 JOIN을 쓰면 부모 정보가 자식 수만큼 복제되어 낭비가 생긴다. 그래서 목록에는 selectin을 쓴다.
- 모델에 `lazy=`로 기본값을 정하거나, 조회할 때 `.options(selectinload(...))`로 필요할 때만 지정한다.
- 모든 관계를 무조건 즉시 로딩하면 불필요한 데이터까지 가져온다. **SQL 로그**(`SQL_ECHO=true`)로 예상대로 조회되는지 검증한다.

## 9. Pydantic과 응답 직렬화

- **Pydantic** = 데이터 **검사관**. `BaseModel`을 상속해 "데이터는 이런 모양"이라고 정의한다.
- 타입 검사, 자동 변환(`"1000"` → `1000`), dict·JSON 변환을 해 준다.
- FastAPI에서는 **입구**(요청 검사, 실패 시 422)와 **출구**(`response_model`로 필요한 필드만 응답)를 지킨다.

| | ORM 모델 | Pydantic 모델 |
|---|---|---|
| 역할 | DB 테이블과 연결 | API 요청·응답 규격 |
| 위치 | `infrastructure/models.py` | `presentation/schemas.py` |

- `from_attributes=True`를 켜면 ORM 객체의 속성(`post.title`)을 읽어 Pydantic 모델로 변환할 수 있다.
- ORM 객체를 그대로 반환하지 말고 응답 스키마를 거친다. 관계 데이터를 응답에 넣으려면 **미리 로딩**해 둬야 직렬화 중 추가 쿼리(에러)가 생기지 않는다.

## 10. 쿼리 조건, 정렬, 페이징

- **조건:** `.where(조건1, 조건2)`는 AND로 묶인다. OR는 `or_()`를 쓴다. 검색은 `icontains`, 범위는 `in_`, `between`, NULL 확인은 `is_(None)`
- **정렬:** `.order_by(col.asc())`, `.order_by(col.desc())`
- **페이징:** `.offset((page - 1) * size).limit(size)`
- 정렬 컬럼을 사용자 입력으로 받을 때는 **화이트리스트**로 검증해 SQL Injection을 막는다.

## 🛠 트러블슈팅 & 질문 해결 과정

**Q1. `TypeError: Additional arguments should be named <dialectname>_<argument>, got 'ondelete'`**
- 원인: `ondelete`를 `ForeignKey()` 괄호 **밖**(`mapped_column` 쪽)에 넣었다.
- 해결: `ForeignKey("boards.id", ondelete="CASCADE")`로 괄호 안에 넣는다.
- 배운 점: `ForeignKey(onupdate=)`는 FK 동작이고, `mapped_column(onupdate=)`는 수정 시각 자동 갱신이다. 이름은 같지만 다른 기능이다.

**Q2. `Mapped[bool]`일까, `Mapped[Boolean]`일까?**
- `Mapped[]`에는 파이썬 타입(`bool`)을, `mapped_column()`에는 DB 타입(`Boolean`)을 넣는다.

**Q3. 수정 테스트에서 `(수정)`이 두 번 붙었다**
- 원인: `/test/2`가 두 번 호출됐다. 새로고침이나 크롬 주소창의 미리 요청(프리페치) 등이 원인이다. 코드가 "현재 이름 앞에 붙이기"라서 호출할 때마다 누적된다.
- 1차 캐시 문제는 아니다. 캐시는 세션(요청) 단위이기 때문이다.
- 배운 점: **GET으로 데이터를 변경하면 안 된다.** 수정은 PATCH/PUT, 삭제는 DELETE를 쓴다.

**Q4. 삭제가 안 됐다**
- 원인: `session.delete(board)`에 `await`를 빼먹었다. `AsyncSession.delete()`는 비동기 함수라서 `await` 없이는 실행되지 않는다.
- 해결: `await session.delete(board)` 다음에 `await session.commit()`

**Q5. commit 없이 수정한 코드도 "잘 작동"한 것처럼 보였다**
- 메모리 속 객체만 바뀌어서 **응답에만** 반영된 것이다. `commit()`이 없으니 세션이 닫히면서 변경이 버려졌고, DB는 그대로였다.
- 배운 점: 결과는 응답만 보지 말고 **DB에서 직접 확인**한다.

**Q6. 튜터님 코드를 보며 발견한 주의점**
- `default=datetime.now(...)`는 서버 시작 시점의 시간으로 고정된다. `lambda`로 감싸야 한다.
- `init_models()`에 auth 모델이 빠져 있었지만, 다른 import 경로를 통해 **우연히** 등록되고 있었다. 새 모델은 직접 등록하자.
- `nullable=True`인 컬럼은 `Mapped[str | None]`으로 타입을 맞추자.
- 비동기에서 `post.board_config`에 바로 접근하면 `MissingGreenlet` 에러가 난다. `joinedload`나 `lazy="joined"`로 미리 로딩하자.
- 테스트 라우터를 두 번 호출하면 PK(`"qna"`) 중복으로 `IntegrityError`가 난다.

- 비동기 ORM의 거의 모든 함정(`expire_on_commit`, `lazy="select"`, `await` 누락)은 **"몰래 일어나는 DB 접근"** 하나로 설명된다는 걸 알게 됐다.
- 세션, commit, refresh가 각각 **메모리**와 **DB** 중 어디에 영향을 주는지 구분하니 헷갈리던 동작이 정리됐다.
