## 2. REVIEW — SSR·CSR 및 HTTP 통신

### A. SSR과 CSR

| 구분 | SSR | CSR |
|---|---|---|
| 전체 명칭 | Server-Side Rendering | Client-Side Rendering |
| 렌더링 위치 | 서버 | 브라우저 |
| 기본 방식 | 서버가 HTML 생성 | 클라이언트가 JavaScript로 화면 구성 |
| 관련 학습 | Jinja2 | React |

**새롭게 연결한 개념**

이전 수업에서 학습한 Jinja2는 서버가 HTML을 만들어 전달하는 SSR 방식과 연결된다.

반면 React는 브라우저에서 화면을 구성하는 CSR 방식으로 사용할 수 있다.

단, React 자체가 반드시 CSR만 사용하는 것은 아니다.

### B. Network 탭을 이용한 HTTP 요청 분석

Chrome 개발자 도구의 Network 탭에서 다음 정보를 확인했다.

- 요청 URL과 파일명
- HTTP Method
- Status Code
- Resource Type
- Response Size
- 요청 소요 시간
- Waterfall을 통한 요청 순서와 처리 시간

**학습 포인트**

브라우저에서 화면이 정상적으로 보이더라도 내부적으로는 HTML, CSS, JavaScript, 이미지 등 여러 요청이 발생한다.

문제가 생겼을 때 Network 탭에서 어떤 요청이 실패했는지 확인할 수 있다.

### B. UploadFile과 File

```python
from fastapi import File, UploadFile
```

| 객체 | 역할 |
|---|---|
| `File()` | 업로드 파일 매개변수 선언 |
| `UploadFile` | 업로드된 파일 정보 및 파일 객체 제공 |
| `Form()` | 파일과 함께 전달되는 일반 텍스트 필드 수신 |

**[개념 보충 예제]**

```python
from fastapi import FastAPI, File, UploadFile

app = FastAPI()

@app.post("/assets")
async def upload_asset(
    file: UploadFile = File(...)
):
    return {
        "filename": file.filename,
        "content_type": file.content_type
    }
```

위 코드는 개념을 설명하기 위한 예제다. 실제 실습에서는 업로드 결과에 파일 크기, 상태, 생성 시각 등 추가 정보가 포함됐다.

### C. multipart/form-data

파일 업로드 시 일반적으로 사용하는 요청 본문 형식이다.

```text
POST /assets

Content-Type: multipart/form-data
```

하나의 요청 안에 파일과 텍스트 필드 등 여러 파트를 담을 수 있다.

**주요 구성**

- `Content-Disposition`: 파트 이름과 파일명
- `Content-Type`: 파트의 미디어 타입
- `boundary`: 각 파트의 경계

### D. MIME Type

MIME(Multipurpose Internet Mail Extensions) 타입은 전송되는 데이터의 미디어 형식을 나타낸다.

| MIME 타입 | 파일 형식 |
|---|---|
| `image/png` | PNG 이미지 |
| `image/jpeg` | JPEG 이미지 |
| `application/pdf` | PDF |
| `text/plain` | 일반 텍스트 |
| `application/json` | JSON |

**주의**

클라이언트가 보낸 MIME 타입은 실제 파일 내용과 다를 수 있다.

따라서 파일 업로드 기능을 구현할 때는 확장자나 MIME 타입만 신뢰하지 않고 별도의 파일 검증을 고려해야 한다.

### E. Postman 파일 업로드 실습

**요청**

```text
POST http://localhost:8000/assets
```

Postman의 Body에서 `form-data`를 선택하고 `file` 키의 타입을 File로 지정한 뒤 이미지 파일을 첨부했다.

**실습 화면에서 확인한 응답**

```json
{
  "id": 1,
  "filename": "스크린샷 2026-09-18 오전 8.23.50.png",
  "file_size": 52106,
  "content_type": "image/png",
  "status": "PENDING",
  "created_at": "2026-10-30T10:45:33.838108"
}
```

**응답 상태**

```text
201 Created
```

**확인한 사항**

1. 서버가 파일 업로드 요청을 처리했다.
2. 파일명과 파일 크기가 응답에 포함됐다.
3. 콘텐츠 타입이 `image/png`로 표시됐다.
4. 파일 상태가 `PENDING`으로 반환됐다.
5. 생성 시각이 기록됐다.

**주의**

`201 Created`는 해당 요청이 성공적으로 처리됐다는 의미다.

다만 화면만으로는 파일이 어느 저장소에 저장됐는지, DB에 실제로 기록됐는지, 이후 `PENDING` 상태가 어떻게 변경되는지는 확인할 수 없다.

## 4. LECTURE NOTE — 비동기 파일 처리와 스트리밍

### A. 동기 파일 I/O와 비동기 파일 I/O

Python의 일반적인 파일 입출력 함수는 동기 방식으로 동작한다.

```python
with open("example.txt", "rb") as file:
    data = file.read()
```

파일 입출력 중 실행 흐름이 대기할 수 있다.

FastAPI의 비동기 요청 처리에서는 작업 성격에 따라 비동기 파일 I/O를 고려할 수 있다.

**외부 패키지 설치**

```bash
uv add aiofiles
```

**[개념 보충 예제]**

```python
import aiofiles

async with aiofiles.open("example.txt", "rb") as file:
    data = await file.read()
```

**주의**

비동기 방식이 항상 더 빠른 것은 아니다.

특히 CPU 연산이 많은 작업은 `async`만으로 해결되지 않는다.

### B. Chunk — 파일을 나누어 처리하기

청크(Chunk)는 데이터를 일정 크기의 작은 단위로 나눈 것이다.

대용량 파일 전체를 메모리에 올리지 않고 조금씩 처리할 수 있다.

**[개념 보충 예제]**

```python
import aiofiles

async with aiofiles.open("upload.bin", "wb") as output:
    while chunk := await file.read(1024 * 1024):
        await output.write(chunk)
```

**처리 흐름**

```text
업로드 파일
   ↓
1MB 읽기
   ↓
파일에 쓰기
   ↓
다음 1MB 읽기
   ↓
반복
   ↓
완료
```

**장점**

- 메모리 사용량 관리
- 대용량 파일 처리에 적합
- 파일 크기에 비례해 전체 내용을 한 번에 메모리에 보관하지 않아도 됨

### C. AsyncGenerator와 yield

`yield`는 데이터를 한 번에 모두 반환하지 않고 순차적으로 제공할 때 사용한다.

**[개념 보충 예제]**

```python
from typing import AsyncGenerator
import aiofiles

async def read_file_chunks(
    path: str
) -> AsyncGenerator[bytes, None]:

    async with aiofiles.open(path, "rb") as file:
        while chunk := await file.read(1024 * 1024):
            yield chunk
```

**핵심**

- `return`: 함수의 결과를 반환하고 종료
- `yield`: 값을 하나씩 제공하고 이후 실행을 이어갈 수 있음
- `async def`와 `yield`를 함께 사용하면 비동기 제너레이터가 됨

**AI Agent와 연결되는 부분**

LLM 응답을 토큰 또는 텍스트 조각 단위로 전송하는 스트리밍도 데이터를 순차적으로 제공한다는 공통점이 있다.

다만 파일 스트리밍과 LLM 토큰 스트리밍은 실제 전송 프로토콜과 구현 방식이 다를 수 있다.

### D. StreamingResponse

```python
from fastapi.responses import StreamingResponse
```

`StreamingResponse`는 이터레이터 또는 비동기 이터레이터에서 제공되는 데이터를 순차적으로 응답할 수 있도록 한다.

**[개념 보충 예제]**

```python
from fastapi.responses import StreamingResponse

@app.get("/download")
async def download_file():
    return StreamingResponse(
        read_file_chunks("example.pdf"),
        media_type="application/pdf"
    )
```

**파일 다운로드 처리 흐름**

```text
클라이언트 요청
    ↓
FastAPI
    ↓
파일을 청크 단위로 읽음
    ↓
StreamingResponse
    ↓
클라이언트에 순차적으로 전달
```

## 5. LECTURE NOTE — 파일 응답 헤더와 캐시

### A. 주요 HTTP Response Header

| 헤더 | 역할 |
|---|---|
| `Content-Type` | 응답 데이터의 미디어 타입 |
| `Content-Length` | 응답 본문의 크기(바이트) |
| `Content-Disposition` | 콘텐츠 표시·다운로드 방식 및 파일명 |
| `Cache-Control` | 캐시 정책 제어 |

### B. Content-Disposition

파일을 브라우저에서 표시할지 다운로드하도록 제안할지 결정할 때 사용한다.

```text
Content-Disposition: inline
```

브라우저가 지원하는 형식이면 화면에 표시할 수 있다.

```text
Content-Disposition: attachment; filename="report.pdf"
```

브라우저에 파일 다운로드를 제안한다.

**주의**

서버는 응답 헤더로 처리 방식을 제안하지만, 실제 동작은 브라우저와 사용자 설정의 영향을 받을 수 있다.

### C. Cache-Control

브라우저는 HTML, CSS, JavaScript, 이미지 등을 캐싱할 수 있다.

이 때문에 파일이 수정됐는데도 이전 내용이 표시될 수 있다.

**대표적인 캐시 설정**

```text
Cache-Control: no-cache
```

캐시된 응답을 재사용하기 전에 재검증하도록 한다.

```text
Cache-Control: no-store
```

응답을 저장하지 않도록 지시한다.

```text
Cache-Control: public, max-age=3600
```

공유 캐시에 저장할 수 있으며 최대 3600초 동안 신선한 응답으로 취급할 수 있다.

**새롭게 이해한 점**

파일을 수정했다고 브라우저가 항상 최신 파일을 즉시 요청하는 것은 아니다.

개발 중 화면이 변경되지 않으면 캐시와 Network 응답 헤더를 확인할 필요가 있다.

## 6. LECTURE NOTE — BackgroundTasks

### A. 백그라운드 작업

FastAPI는 `BackgroundTasks`를 이용해 응답을 보낸 뒤 실행할 작업을 등록할 수 있다.

```python
from fastapi import BackgroundTasks
```

**[개념 보충 예제]**

```python
from fastapi import FastAPI, BackgroundTasks

app = FastAPI()

def process_asset(asset_id: int):
    print(f"파일 {asset_id} 후처리")

@app.post("/assets/process")
async def create_task(
    background_tasks: BackgroundTasks
):
    background_tasks.add_task(process_asset, 1)

    return {"message": "처리 요청 접수"}
```

**처리 흐름**

```text
클라이언트 요청
    ↓
FastAPI 요청 처리
    ↓
백그라운드 작업 등록
    ↓
클라이언트에 응답 전송
    ↓
백그라운드 작업 실행
```

**활용 예시**

- 이메일 발송
- 파일 업로드 후 후처리
- 로그 기록
- 이미지 썸네일 생성 요청

**주의**

FastAPI의 `BackgroundTasks`는 별도 작업 큐나 독립 프로세스를 자동으로 생성하는 기능은 아니다.

작업의 내구성, 실패 시 재시도, 결과 추적이 중요하다면 별도 작업 큐를 고려해야 한다.

### B. 파일 업로드 실패 처리

**강의에서 강조한 부분**

업로드 도중 오류가 발생하면 이미 생성된 파일이나 임시 데이터를 정리해야 한다.

**설계 시 고려할 사항**

1. 업로드 시작
2. 파일 저장
3. 메타데이터 기록
4. 후처리 실행
5. 오류 발생 시 파일 및 관련 데이터 정리
6. 적절한 HTTP 오류 응답 반환

**주의**

파일 저장과 DB 기록은 서로 다른 시스템에 걸친 작업일 수 있다.

따라서 예외가 발생했을 때 어떤 자원이 이미 생성됐는지 확인하고 정리해야 한다.

## 7. LECTURE NOTE — 5장 2강: ORM과 데이터베이스 연결

### A. ORM — Object-Relational Mapping

ORM은 객체지향 프로그램의 객체와 관계형 데이터베이스의 테이블을 연결하는 기술이다.

**관련 개념**

- OOP (Object-Oriented Programming): 객체지향 프로그래밍
- ORM (Object-Relational Mapping): 객체 관계 매핑
- RDBMS (Relational Database Management System): 관계형 데이터베이스 관리 시스템

**강의 비유: ORM은 번역기**

```text
Python 객체
    ↓
ORM
    ↓ SQL
RDBMS
    ↓ 조회 결과
ORM
    ↓
Python 객체
```

**새롭게 이해한 점**

ORM을 사용하면 Python 객체를 중심으로 데이터베이스 작업을 표현할 수 있다.

다만 ORM이 SQL을 없애는 것은 아니다. 내부적으로 SQL을 생성하거나 실행한다.

### B. ORM을 사용하는 이유

- 객체 중심의 코드 작성
- 반복적인 SQL 작성 감소
- 데이터 모델과 DB 구조의 매핑
- 데이터베이스 작업의 일관성 확보
- DBMS 변경 시 일부 차이 추상화

**주의**

ORM을 사용한다고 데이터베이스 종속성이 완전히 사라지는 것은 아니다.

특정 DBMS의 기능이나 SQL 문법에 의존하는 코드는 별도 수정이 필요할 수 있다.

### C. Connection Pool — 연결 풀

데이터베이스에 요청할 때마다 새 연결을 생성하면 비용이 발생한다.

연결 풀(Connection Pool)은 미리 생성했거나 재사용 가능한 DB 연결을 관리한다.

**강의 비유**

매번 새로운 직원을 채용하는 대신, 대기 중인 직원을 필요한 작업에 배정하는 것과 비슷하다.

```text
FastAPI 요청
     ↓
Connection Pool
  ┌────┬────┬────┐
  │ C1 │ C2 │ C3 │
  └────┴────┴────┘
     ↓
 PostgreSQL
```

**장점**

- 연결 생성 비용 감소
- 동시 요청 처리 지원
- DB 연결 수 관리

### D. Connection Pool 주요 설정

| 옵션 | 의미 |
|---|---|
| `pool_size` | 기본적으로 유지할 연결 풀 크기 |
| `max_overflow` | 기본 풀 크기를 초과해 추가로 만들 수 있는 연결 수 |
| `pool_timeout` | 연결을 기다릴 최대 시간 |
| `pool_recycle` | 일정 시간이 지난 연결을 재생성하도록 관리 |
| `pool_pre_ping` | 연결을 사용하기 전에 유효성 확인 |

**pool_pre_ping**

오랫동안 사용하지 않은 DB 연결은 서버나 네트워크에 의해 끊어질 수 있다.

`pool_pre_ping=True`는 연결을 체크아웃할 때 유효한지 확인하고, 끊어진 연결을 교체하도록 돕는다.

**pool_recycle**

연결이 일정 시간 이상 오래됐다면 다음 사용 시 재생성하도록 관리한다.

**주의**

`pool_pre_ping`은 주기적으로 백그라운드에서 모든 연결에 `SELECT`를 실행한다는 뜻이 아니다.

일반적으로 연결을 풀에서 가져오는 시점에 연결 유효성을 확인한다.

### E. 비동기 DB 패키지 설치

**실습 명령어**

```bash
uv add fastapi uvicorn pydantic sqlalchemy asyncpg greenlet python-dotenv
```

| 패키지 | 역할 |
|---|---|
| `fastapi` | API 프레임워크 |
| `uvicorn` | ASGI 서버 |
| `pydantic` | 데이터 검증 |
| `sqlalchemy` | ORM 및 SQL 도구 |
| `asyncpg` | PostgreSQL 비동기 드라이버 |
| `greenlet` | SQLAlchemy 내부의 일부 실행 흐름 지원 |
| `python-dotenv` | `.env` 환경 변수 로딩 |

**주의**

`.env.local`에 비밀번호나 API 키를 넣는 경우 Git에 업로드되지 않도록 관리해야 한다.

### C. logger.py — 공통 로깅 설정

**실습 화면의 코드 구조**

```python
import os
import logging
from dotenv import load_dotenv

load_dotenv()

logging.basicConfig(
    level=logging.DEBUG if os.getenv("LOGGING_MODE") == "debug"
    else logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s %(filename)s - %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S"
)

logger = logging.getLogger(
    os.environ.get("LOGGER_NAME", "app")
)
```

**주요 구성**

- `load_dotenv()`: 환경 변수 파일 로딩
- `os.getenv()`: 환경 변수 조회
- `logging.DEBUG`: 상세 로그 출력
- `logging.INFO`: 일반 로그 출력
- `logging.basicConfig()`: 기본 로깅 설정
- `logging.getLogger()`: 이름을 가진 로거 생성

**로그 포맷**

| 표현식 | 의미 |
|---|---|
| `%(asctime)s` | 로그 발생 시각 |
| `%(levelname)s` | 로그 레벨 |
| `%(name)s` | 로거 이름 |
| `%(filename)s` | 파일명 |
| `%(message)s` | 로그 메시지 |

**[코드 검토]**

실습 화면에서는 `.env.local` 파일이 별도로 존재하지만 `load_dotenv()`에 파일 경로를 지정하지 않았다.

`load_dotenv()`는 일반적으로 `.env` 파일을 자동 탐색하므로, `.env.local`을 사용하려면 명시적으로 경로를 지정하는 편이 안전하다.

```python
load_dotenv(".env.local")
```

또한 `logging.basicConfig()`는 이미 로깅 핸들러가 설정된 경우 기대한 대로 재설정되지 않을 수 있다.
