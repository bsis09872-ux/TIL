# 4계층 아키텍처 · DDD 용어 정리 (떡볶이 비유)

## 1. 용어 정리: "하나를 여러 이름으로 부르는" 느낌이 드는 이유

DDD 용어는 서로 다른 **크기(범위)** 를 가리킵니다. 큰 것부터 작은 것 순서로 보면 정리됩니다.

| 크기 | 용어 | 뜻 | 떡볶이 비유 |
| --- | --- | --- | --- |
| 가장 큼 | **도메인** | 해결하려는 업무 영역 전체 | 식당 운영 전체 |
| ↓ | **하위 도메인** (= 노트의 "문제 영역") | 도메인을 업무별로 나눈 덩어리 | 요리, 주문, 결제 |
| ↓ | **바운디드 컨텍스트** | 하위 도메인을 실제로 구현하는 경계. 이 안에서는 용어의 뜻이 하나로 통일됨 | 주방(요리), 카운터(주문) |
| ↓ | **애그리거트** | 함께 바뀌고 함께 일관성을 지켜야 하는 객체 묶음 | 떡볶이 레시피 + 재료 목록 + 조리 단계 |
| ↓ | **애그리거트 루트** | 애그리거트의 대표 엔티티. 바깥에서는 루트를 통해서만 접근 | 떡볶이 레시피 (Recipe) |
| ↓ | **엔티티** | 고유 ID가 있어서 값이 바뀌어도 같은 대상으로 취급 | 레시피 (id=1번 레시피는 양념을 바꿔도 1번) |
| 가장 작음 | **값 객체 (VO)** | ID 없이 값 자체가 의미. 값이 같으면 같은 것 | "대파 1대", "고추장 2큰술" |

노트에서 고칠 부분이 두 군데 있습니다.

- "전체 레시피를 ROOT라고 하고, 각 요소는 VO" → **반은 맞습니다.** 레시피가 루트인 것은 맞지만, 요소 전부가 VO는 아닙니다. "대파 1대"처럼 값만 의미 있는 것이 VO이고, 조리 단계처럼 순번(ID)으로 구분해야 하는 것은 애그리거트 내부의 엔티티일 수 있습니다.
- "떡볶이 레시피는 엔티티" → 맞습니다. 정확히는 **엔티티이면서 애그리거트 루트**입니다. 루트는 항상 엔티티입니다.

한 문장으로 묶으면: **떡볶이 레시피(루트 엔티티)가 재료(VO)와 조리 단계를 거느린 묶음이 애그리거트**이고, 조리법을 보려면 레시피를 거쳐야 합니다. 그래야 "양념은 마지막에" 같은 규칙을 레시피 한 곳에서 지킬 수 있습니다.

## 2. 도메인 계층 노트 교정: "핸드믹서"는 도메인에 들어가면 안 됨

노트의 "핸드믹서로 양념을 만든다"에는 **기술(핸드믹서)** 이 섞여 있습니다. 도메인은 기술을 모르는 것이 핵심이므로 이렇게 나눕니다.

| 계층 | 내용 |
| --- | --- |
| 도메인 (명세) | "양념은 곱게 갈아야 한다" → 추상 메서드 `grind(재료)` |
| 인프라 (구현) | LG 핸드믹서로 갈기, 절구로 빻기 → 추상 메서드를 구현한 클래스 |

인프라 목록의 "3. 양념 만들기"도 기술이 아니라 **조리 절차(도메인 규칙)** 라서 도메인 쪽으로 옮겨야 합니다. 인프라에 남는 것은 동네마트, LG 핸드믹서, 채칼처럼 바꿔 끼울 수 있는 도구뿐입니다.

용어 하나도 짚으면, 이렇게 도메인이 정의하고 인프라가 구현하는 추상 클래스는 보통 **인터페이스(포트)/리포지토리**라고 부르고, 올려주신 자료에서는 ACL 자리입니다. **도메인 서비스**는 조금 다른 개념으로, 한 엔티티에 넣기 애매한 규칙(예: 회원 등급 + 쿠폰으로 최종 가격 계산)을 담는 곳입니다.

## 3. 질문 답변: 바운디드 컨텍스트와 테이블

### 다른 영역의 데이터를 써도 되나?

**읽는 것은 됩니다. 단, 직접 테이블을 건드리지 말고 그 영역 담당자가 만든 창구(서비스/리포지토리)를 통해서** 가져옵니다. 경계는 "접근 금지"가 아니라 **"규칙의 주인은 한 명"** 이라는 뜻입니다.

특히 쓰기는 반드시 주인을 거쳐야 합니다. 경매 낙찰 시 지갑 테이블의 잔액을 직접 `UPDATE` 하면 "잔액은 음수가 될 수 없다" 같은 지갑의 규칙을 우회하게 됩니다. 대신 지갑 쪽 메서드를 호출합니다.

```python
# 경매(application) 서비스 안에서
await wallet_service.withdraw(buyer_id, price)      # 지갑 규칙은 지갑이 검사
await inventory_service.transfer(item_id, buyer_id) # 아이템 이동은 인벤토리가 처리
```

노트에 적으신 회원/주문 예시가 바로 이 개념입니다. 같은 사람이라도 **회원 컨텍스트**에서는 ID, PASSWORD, NAME, EMAIL, ADDRESS를 가진 "회원"이고, **주문 컨텍스트**에서는 NAME, EMAIL만 필요한 "주문자"입니다. 주문 쪽은 `user_id`만 저장해 두고, 필요할 때 회원 쪽에서 필요한 값만 받아 자기 모델(주문자)로 바꿔 씁니다.

### 다른 사람 테이블이 아직 없으면?

올려주신 자료의 "명세와 구현 분리"가 정확히 이 상황을 위한 것입니다.

1. 팀원과 **인터페이스(추상 클래스)를 먼저 합의**합니다. 예: `WalletRepository.find_by_user_id()`, `save()`
2. 진짜 구현이 나오기 전까지는 **메모리 딕셔너리로 만든 가짜 구현**으로 개발합니다 (1장의 `in_memory_db`와 같은 방식)
3. 팀원의 PostgreSQL 구현이 완성되면 갈아 끼웁니다. 내 응용 서비스 코드는 바뀌지 않습니다.

### 테이블을 매번 새로 불러오나?

아닙니다. 여기서 혼동이 생긴 것 같은데, **테이블과 데이터(행)를 구분**하면 풀립니다.

- **테이블** = 서랍장. 프로젝트 시작 시 마이그레이션(Alembic 등)으로 **한 번** 만들어 두고 계속 존재합니다. 팀원 모두의 테이블이 같은 DB 안에 동시에 존재합니다.
- **행(row)** = 서랍에 넣는 물건. 물고기를 낚을 때마다, 경매가 끝날 때마다 생기는 것은 테이블이 아니라 **행 하나(`INSERT`)** 입니다.

낚시&경매 게임이라면 `fish_catches`, `auctions`, `wallets` 같은 테이블은 처음에 한 번 만들어지고, 게임 중에는 거기에 기록이 쌓이기만 합니다. 요청마다 새로 여는 것은 테이블이 아니라 DB **연결(세션)** 이고, 이것도 커넥션 풀에서 재사용됩니다.

## 4. 한 줄 요약

레시피(도메인)는 "무엇을 지켜야 하는지"만 알고, 요리사(응용)는 레시피를 보며 순서를 진행하고, 마트·믹서(인프라)는 명세에 맞춰 바꿔 끼우며, 다른 주방(컨텍스트)의 재료가 필요하면 그 주방에 요청하지 남의 냉장고를 직접 열지 않는다.
