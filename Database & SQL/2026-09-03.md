# REVIEW

## 1. 데이터 무결성 3가지

**데이터 무결성(Data Integrity)**은 Database의 데이터가 **정확하고 일관된 상태를 유지하도록 하는 것**이다.

| 무결성 | 핵심 | 대표적인 구현 |
|---|---|---|
| **도메인 무결성** | Column에 허용되는 값의 범위·형식 유지 | Data Type, `CHECK`, `NOT NULL` 등 |
| **개체 무결성** | 각 Row를 고유하게 식별 | `PRIMARY KEY` |
| **참조 무결성** | Table 간 참조 관계의 일관성 유지 | `FOREIGN KEY` |

> **도메인 무결성은 단순히 Data Type만 의미하지 않는다.**  
> 자료형뿐 아니라 해당 Column에 들어갈 수 있는 **값의 범위와 규칙**까지 포함한다.

---

## 2. 왜 DB와 SQL을 별도로 사용하는가?

> **Q. Excel, Python, Pandas 등 다른 Tool로도 데이터를 합치고 수정할 수 있는데 왜 Database와 SQL이라는 별도의 시스템과 언어를 사용할까?**

단순히 데이터를 **한 번 합치고 분석하는 것**과 여러 사용자가 사용하는 데이터를 **지속적으로 저장하고 관리하는 것**은 목적이 다르다.

```text
Excel / Pandas
→ 파일 또는 메모리에 있는 데이터를 불러옴
→ 가공 / 분석
→ 결과 생성

Database
→ 데이터를 구조적으로 저장
→ 여러 프로그램과 사용자가 지속적으로 접근
→ 무결성 / 권한 / 관계 / 트랜잭션 등을 관리

SQL
→ Database에
   "무엇을 저장하고"
   "무엇을 찾고"
   "무엇을 수정할지"
   명령하는 언어
```

즉,

> **DB의 핵심 목적 = 데이터를 안정적이고 구조적으로 저장·관리**  
> **SQL의 핵심 목적 = 관계형 DB의 데이터를 정의·조회·조작·제어**

Python과 SQL은 경쟁 관계라기보다 실제 서비스에서 함께 사용된다.

```text
Python Application
       ↓
      SQL
       ↓
     DBMS
       ↓
   Database
```

# LECTURE NOTE

## 1. SQL 명령어의 분류

SQL은 목적에 따라 크게 다음과 같이 구분할 수 있다.

| 분류 | Full Name | 목적 | 대표 명령어 |
|---|---|---|---|
| **DDL** | Data Definition Language | 구조 정의 | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` |
| **DML** | Data Manipulation Language | 데이터 조작 | `INSERT`, `UPDATE`, `DELETE` |
| **DQL** | Data Query Language | 데이터 조회 | `SELECT` |
| **DCL** | Data Control Language | 권한 제어 | `GRANT`, `REVOKE` |
| **TCL** | Transaction Control Language | 트랜잭션 제어 | `COMMIT`, `ROLLBACK` |

※ `SELECT`를 DML에 포함하여 분류하기도 하고, **DQL로 별도로 분류**하기도 한다.

### DDL

```text
CREATE    → 생성
ALTER     → 구조 변경
DROP      → 객체 제거
TRUNCATE  → Table 구조는 유지하면서 데이터 전체 제거
```

### DML

```text
INSERT → 추가
UPDATE → 수정
DELETE → 삭제
SELECT → 조회
```

### DCL

```text
GRANT  → 권한 부여
REVOKE → 권한 회수
```

### TCL

```text
COMMIT   → Transaction의 변경 사항을 확정
ROLLBACK → 아직 확정되지 않은 변경 사항을 되돌림
```

> `COMMIT`과 `ROLLBACK`은 단순히 파일을 저장하고 취소하는 개념보다는 **Transaction 단위의 변경을 확정하거나 되돌리는 명령어**로 이해한다.

# 2. DDL - 데이터 정의어

## 2-1. CREATE

Database 객체를 생성한다.

### Table 생성

```sql
CREATE TABLE 테이블명 (
    컬럼명1 데이터타입 [제약조건],
    컬럼명2 데이터타입 [제약조건],
    ...
);
```

`[]`로 표현한 부분은 **선택적으로 사용할 수 있는 요소**라는 의미이다.

---

## 2-2. Constraint - 제약조건

제약조건은 Database에 **잘못된 데이터가 들어오는 것을 제한하여 무결성을 유지**하는 규칙이다.

### PRIMARY KEY

```sql
id INTEGER PRIMARY KEY
```

- 중복 허용 ❌
- `NULL` 허용 ❌
- Row를 고유하게 식별

여러 Column의 조합으로 하나의 Primary Key를 만들 수도 있다.

```sql
CREATE TABLE 테이블명 (
    컬럼1 INTEGER,
    컬럼2 INTEGER,
    
    PRIMARY KEY (컬럼1, 컬럼2)
);
```

이를 **복합키(Composite Key)**라고 한다.

---

### NOT NULL

```sql
name VARCHAR(50) NOT NULL
```

해당 Column에 `NULL`을 허용하지 않는다.

즉, **반드시 값이 필요한 필수 항목**을 표현할 때 사용할 수 있다.

---

### UNIQUE

```sql
email VARCHAR(100) UNIQUE
```

Column의 값이 중복되지 않도록 제한한다.

```text
PRIMARY KEY
→ UNIQUE + NOT NULL의 성격
→ Table의 대표 식별자

UNIQUE
→ 중복 방지
→ NULL 처리 방식은 DBMS에 따라 차이가 있을 수 있음
```

PostgreSQL의 기본 `UNIQUE` 제약에서는 여러 개의 `NULL`이 허용될 수 있다.

`NULL`까지 허용하지 않으려면 다음처럼 함께 사용하면 된다.

```sql
email VARCHAR(100) UNIQUE NOT NULL
```

---

### CHECK

특정 조건을 만족하는 값만 저장하도록 제한한다.

```sql
age INTEGER CHECK (age >= 0)
```

논리 연산자를 함께 사용할 수도 있다.

```sql
CHECK (age >= 0 AND age <= 120)
```

```text
AND
OR
NOT
```

등을 이용해 조건을 구성할 수 있다.

---

### DEFAULT

값을 직접 입력하지 않았을 때 사용할 **기본값**을 지정한다.

```sql
status VARCHAR(20) DEFAULT 'READY'
```

내장 함수를 이용할 수도 있다.

```sql
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

# 4. KEY와 무결성

## 4-1. Primary Key (PK)

```text
PRIMARY KEY
      ↓
Row를 고유하게 식별
      ↓
개체 무결성
```

---

## 4-2. Foreign Key (FK)

**Foreign Key(외래키)**는 다른 Table의 Key를 참조하여 **Table 사이의 관계를 만드는 Column**이다.

```text
부모 Table
     ↑
     │ 참조
     │
Foreign Key
     │
자식 Table
```

Foreign Key가 있는 쪽을 일반적으로 **자식 Table**, 참조되는 쪽을 **부모 Table**이라고 한다.

### REFERENCES

```sql
CREATE TABLE 테이블명 (
    컬럼명 자료형 REFERENCES 부모테이블(컬럼명)
);
```

예:

```sql
CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY,
    member_id INTEGER REFERENCES members(member_id)
);
```

```text
MEMBERS (부모)
member_id = 10
      ↑
      │ FK
      │
ORDERS (자식)
member_id = 10
```

> `PRIMARY KEY → 개체 무결성`  
> `FOREIGN KEY → 참조 무결성`  
> `Data Type / CHECK 등의 Domain Constraint → 도메인 무결성`

# 5. Foreign Key와 참조 동작

Foreign Key를 사용하면 **부모 Table에 존재하지 않는 값을 자식 Table에서 참조할 수 없다.**

```text
MEMBERS

member_id
1
2
3
```

여기에서 `member_id = 100`이 존재하지 않는다면:

```text
ORDERS
member_id = 100  ❌
```

와 같은 참조를 허용하지 않는다.

---

## 부모 데이터를 삭제하면?

기본적으로 자식이 부모를 참조하고 있다면 부모 Row 삭제가 제한될 수 있다.

하지만 Foreign Key를 만들 때 삭제 규칙을 지정할 수 있다.

### ON DELETE CASCADE

```sql
REFERENCES members(member_id)
ON DELETE CASCADE
```

```text
부모 삭제
   ↓
연결된 자식도 함께 삭제
```

### ON DELETE SET NULL

```sql
REFERENCES members(member_id)
ON DELETE SET NULL
```

```text
부모 삭제
   ↓
자식 Row는 유지
   ↓
Foreign Key → NULL
```

※ 해당 Foreign Key Column이 `NULL`을 허용해야 한다.

| 옵션 | 부모 삭제 | 자식 Row | FK 값 |
|---|---|---|---|
| 기본적인 제한 동작 | 참조 중이면 삭제 제한 | 유지 | 유지 |
| `ON DELETE CASCADE` | 가능 | **함께 삭제** | Row 자체 삭제 |
| `ON DELETE SET NULL` | 가능 | **유지** | `NULL` |

> 이러한 제약조건의 목적은 **Database의 데이터 관계와 무결성을 유지하는 것**이다.

# 6. 데이터베이스 정규화

## 6-1. Normalization

**Normalization(정규화)**은 데이터 중복과 이상 현상을 줄이기 위해 **Table의 구조를 단계적으로 개선하는 과정**이다.

핵심 목적:

```text
데이터 중복(Redundancy) 감소
            +
이상 현상(Anomaly) 방지
```

---

## 6-2. 이상 현상 (Anomaly)

하나의 Table에 서로 다른 역할의 정보가 반복해서 저장되면 데이터의 일관성을 유지하기 어려워질 수 있다.

### 삽입 이상 (Insertion Anomaly)

필요한 정보를 원하는 방식으로 **추가하기 어려운 문제**

### 갱신 이상 (Update Anomaly)

동일한 정보가 여러 곳에 중복되어 있어 **일부만 수정되면서 데이터가 서로 달라지는 문제**

### 삭제 이상 (Deletion Anomaly)

하나의 데이터를 삭제했는데 **유지해야 할 다른 정보까지 함께 사라지는 문제**

그래서 서로 다른 역할의 데이터를 Table로 분리한다.

```text
학생 테이블
학생번호 | 이름 | 전화번호

동아리 테이블
동아리번호 | 동아리명 | 장소

가입 테이블
학생번호 | 동아리번호
```

---

# 6-3. 제1정규형 (1NF)

**First Normal Form**

> 한 Cell에는 하나의 값, 즉 **Atomic Value(원자값)**만 저장한다.

❌

| 학생 | 전화번호 |
|---|---|
| A | 010-1111, 010-2222 |

⭕ 한 속성의 값이 원자적으로 표현되도록 구조를 설계한다.

> **1NF = 한 칸에는 하나의 값**

---

# 6-4. 제2정규형 (2NF)

**Second Normal Form**

2NF에서는 **Partial Dependency(부분 함수 종속)**을 제거한다.

특히 **복합키(Composite Key)**를 사용하는 Table에서 중요하다.

```text
복합 Primary Key
(A + B)
   ↓
일반 Column이
A 또는 B 하나에만 종속되어 있음
   ↓
Partial Dependency
```

따라서,

> **2NF = 복합키 전체가 아니라 키의 일부에만 의존하는 Column을 분리하자.**

---

## 💡 기업 데이터 예시로 이해하기

> **Q. 기업 데이터를 받았는데 산업 구분을 위해 SIC, GICS, SIC Industry Name, GICS Industry Name 등을 전부 받았다. 필요 없는 것을 삭제하거나 Table을 분리하는 것이 2NF인가?**

**단순히 Column이 많거나 필요 없는 Column을 삭제하는 것 자체는 2NF가 아니다.**

2NF의 핵심은 **Column의 개수가 아니라 함수적 종속 관계**이다.

예를 들어 다음과 같은 데이터가 있다고 하자.

```text
(Firm_ID, Year) ← 복합키

Firm_ID | Year | Sales | SIC_Code | SIC_Name
```

여기서:

```text
(Firm_ID, Year) → Sales
```

Sales는 특정 **기업 + 연도**가 결정해야 한다.

그런데 만약 기업의 산업분류가 해당 기간 동안 고정되어 있다고 단순화하면:

```text
Firm_ID → SIC_Code
```

처럼 `SIC_Code`가 복합키 전체가 아니라 `Firm_ID`에만 종속될 수 있다.

이런 구조라면 **부분 함수 종속**을 검토할 수 있다.

하지만:

```text
SIC
GICS
SIC_Name
GICS_Name
```

을 많이 받아서 그중 필요 없는 Column을 제거하는 것은 주로 **데이터 정리(Data Cleaning) 또는 Feature Selection**의 문제이지, 그 자체로 2NF라고 부르는 것은 아니다.

> **핵심:**  
> `Column이 많다 → 2NF 문제 ❌`  
> `복합키 일부에만 종속되는 일반 속성이 있다 → 2NF 검토 ⭕`

---

# 6-5. 제3정규형 (3NF)

**Third Normal Form**

3NF에서는 **Transitive Dependency(이행 함수 종속)**을 제거한다.

예:

```text
학생번호 → 학과번호
학과번호 → 학과명

따라서

학생번호 → 학과명
```

`학과명`이 학생번호에 직접적으로 의존한다기보다 **학과번호를 거쳐 간접적으로 결정**된다.

이를 분리하면:

```text
STUDENT
학생번호 | 이름 | 학과번호

DEPARTMENT
학과번호 | 학과명
```

처럼 구성할 수 있다.

> **3NF = Key가 아닌 Column을 통해 또 다른 Column이 결정되는 구조를 분리하자.**

---

## 6-6. 1NF → 2NF → 3NF 한 번에 보기

```text
1NF
한 Cell에 하나의 값
      ↓
Atomic Value

2NF
복합키 일부에만 의존?
      ↓
Partial Dependency 제거

3NF
일반 Column이 다른 일반 Column에 의존?
      ↓
Transitive Dependency 제거
```

| 단계 | 제거하는 문제 | 기억할 질문 |
|---|---|---|
| **1NF** | 반복·다중 값 | 한 칸에 값이 하나인가? |
| **2NF** | 부분 함수 종속 | 복합키 전체에 의존하는가? |
| **3NF** | 이행 함수 종속 | 일반 속성이 다른 일반 속성에 의존하는가? |

---

## 6-7. BCNF

**BCNF (Boyce-Codd Normal Form)**에서는 함수 종속 관계의 **모든 결정자(Determinant)가 후보키(Candidate Key)**가 되도록 요구한다.

```text
Determinant
    ↓
Candidate Key
```

3NF보다 조금 더 엄격한 정규형이다.

---

# 6-8. 정규화가 항상 정답일까?

**정규화를 많이 할수록 무조건 좋은 Database가 되는 것은 아니다.**

정규화를 진행하면:

```text
중복 감소
무결성 향상
수정 용이
```

이라는 장점이 있지만 Table이 많이 분리되면서 데이터를 조회할 때 여러 Table을 **JOIN**해야 할 수 있다.

```text
정규화 ↑
   ↓
Table 분리 ↑
   ↓
JOIN 필요 ↑
   ↓
조회 구조 복잡성 / 성능 비용 증가 가능
```

그래서 실제 시스템에서는 목적에 따라 **Denormalization(반정규화)**을 선택하기도 한다.

> 중요한 것은 **무조건 Table을 많이 나누는 것이 아니라 데이터의 일관성·조회 패턴·성능·운영 구조를 고려하여 적절한 수준으로 설계하는 것**이다.

### MSA와 정규화

**MSA(Microservices Architecture)에서는 정규화를 하지 않는 것이 일반적이라고 단순화하면 안 된다.**

MSA의 중요한 설계 원칙 중 하나는 서비스별로 데이터의 **소유 경계(Boundary)**를 분리하는 것이다.

```text
회원 Service → 회원 DB
주문 Service → 주문 DB
결제 Service → 결제 DB
```

각 서비스 **내부의 Database에서는 필요에 따라 정규화를 적용**할 수 있다.

다만 서로 다른 서비스의 DB를 하나의 관계형 DB처럼 강하게 JOIN하고 FK로 결합하면 서비스 간 의존성이 커질 수 있으므로 **서비스 사이의 결합도를 낮추는 설계**가 중요하다.

> **정규화 문제와 MSA의 서비스 분리 문제는 서로 관련될 수 있지만 같은 개념은 아니다.**

# 7. PostgreSQL 실습 명령어

## 7-1. PostgreSQL Docker Container 접속

```bash
docker exec -it postgres bash
```

- `docker exec` → 실행 중인 Container 안에서 명령 실행
- `-it` → 터미널을 대화형으로 사용
- `postgres` → Container 이름
- `bash` → Linux에서 사용하는 Shell 중 하나

---

## 7-2. PostgreSQL 접속

```bash
psql -U postgres
```

- `psql` → PostgreSQL의 Command Line Client
- `-U` → 접속할 사용자 지정
- `postgres` → 사용자 계정명

```text
Terminal
   ↓
Docker Container
   ↓
psql
   ↓
PostgreSQL
```

---

## 7-3. Table 명세 확인

`psql`에서:

```text
\d 테이블명
```

Table의 Column, Data Type, Constraint 등의 구조를 확인할 수 있다.

# 💡 오늘의 핵심 흐름

```text
Database
   ↓
데이터를 안정적으로 관리하려면?
   ↓
Data Integrity
   │
   ├─ Domain Integrity
   ├─ Entity Integrity
   └─ Referential Integrity
            ↓
     Constraint / KEY
       │           │
       PK          FK
       ↓           ↓
   개체 무결성   참조 무결성
            ↓
        SQL 사용
   ┌────────┼────────┐
  DDL      DML      DCL/TCL
   ↓
CREATE TABLE
   ↓
데이터가 중복되면?
   ↓
Anomaly
   ↓
Normalization
   ↓
1NF → 2NF → 3NF
   ↓
필요하면 더 엄격한 BCNF
   ↓
실제 시스템에서는
무결성 + 성능 + 사용 목적을 함께 고려
```

> **오늘의 핵심:** SQL은 단순히 데이터를 조회하는 문법이 아니라, Database의 **구조를 정의하고 데이터를 조작하며 무결성을 유지하는 수단**이다. 정규화 역시 Table을 무조건 나누는 기술이 아니라 **데이터의 종속 관계를 정리하여 중복과 이상 현상을 줄이는 설계 과정**이다.
