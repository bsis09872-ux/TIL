## 🔄 REVIEW

### Subquery, NOT IN과 NULL

Subquery 결과에 `NULL`이 포함되어 있을 때 `NOT IN`을 사용하면 SQL의 NULL 처리 때문에 예상과 다르게 결과가 나오지 않을 수 있다.

```sql
WHERE id NOT IN (1, 2, NULL)
```

따라서 상황에 따라 `NULL`을 제외하거나 `NOT EXISTS` 사용을 고려한다.

```sql
IS NOT NULL
```

```sql
NOT EXISTS (...)
```

### IN vs EXISTS

`IN`과 `EXISTS` 중 어떤 방법이 실제로 효율적인지는 실행 계획을 통해 확인할 수 있다.

```sql
EXPLAIN ANALYZE
...
```

> **`IN`과 `EXISTS` 중 항상 하나가 빠른 것은 아니므로 실제 Query Plan을 확인한다.**

# 📚 LECTURE NOTE

# 1. Transaction & ACID

## 1-1. Transaction

**Transaction(트랜잭션)**은 여러 SQL 작업을 **하나의 논리적인 실행 단위**로 묶는 것이다.

```text
Transaction
     ↓
여러 SQL 작업
     ↓
┌────┴────┐
성공      실패
 ↓         ↓
COMMIT  ROLLBACK
```

### 기본 명령어

```sql
BEGIN;

-- SQL 작업

COMMIT;
```

- `BEGIN` → Transaction 시작
- `COMMIT` → 작업을 확정하여 DB에 영구 반영
- `ROLLBACK` → COMMIT 전 Transaction의 변경사항 취소

```text
BEGIN
  ↓
SQL 실행
  ↓
COMMIT
  ↓
DB 영구 반영
```

---

## 1-2. ACID 원칙

Transaction이 안전하고 일관되게 처리되기 위한 네 가지 핵심 원칙이다.

| 원칙 | 의미 | 핵심 |
|---|---|---|
| **Atomicity** | 원자성 | All or Nothing |
| **Consistency** | 일관성 | DB 규칙과 제약조건 유지 |
| **Isolation** | 격리성 | 동시 Transaction 간 간섭 제어 |
| **Durability** | 지속성 | COMMIT 결과 영구 보존 |

### ① Atomicity - 원자성

Transaction 안의 작업은 **모두 성공하거나 모두 실패**해야 한다.

```text
작업 A 성공
작업 B 성공
작업 C 실패
     ↓
전체 작업 취소
```

> `ROLLBACK` 자체가 ACID 원칙인 것은 아니며, **Atomicity를 구현하는 데 사용되는 기능**이다.

### ② Consistency - 일관성

Transaction 실행 전후로 DB가 정의한 규칙과 제약조건을 만족하는 상태를 유지해야 한다.

```text
PRIMARY KEY
FOREIGN KEY
UNIQUE
CHECK
...
```

### ③ Isolation - 격리성 ⭐

여러 Transaction이 동시에 실행될 때 서로의 작업이 부적절하게 간섭하지 않도록 제어한다.

대표적인 예:

```text
콘서트 좌석 1개 남음

사용자 A ─┐
          ├─ 동시에 구매 시도
사용자 B ─┘
```

이런 **Concurrency(동시성) 문제**를 제어하기 위해 상황에 따라 Row Lock을 사용할 수 있다.

```sql
SELECT ...
FOR UPDATE;
```

`FOR UPDATE`는 조회한 Row를 다른 Transaction이 동시에 변경하는 상황을 제어하기 위해 사용할 수 있다.

### ④ Durability - 지속성

```text
COMMIT
   ↓
Transaction 확정
   ↓
DB에 영구 반영
```

COMMIT된 Transaction의 결과는 이후에도 보존되어야 한다.

# 2. Transaction 실습

## 2-1. COMMIT 전

환경:

```text
Supabase
└─ ax-study
```

```sql
BEGIN;

INSERT INTO users (email)
VALUES ('user02@test.org');

SELECT * FROM users;
```

현재 Transaction 안에서는 INSERT한 데이터를 조회할 수 있지만 아직 `COMMIT`되지 않은 상태다.

다른 세션에서는 해당 변경사항이 아직 보이지 않을 수 있다.

---

## 2-2. COMMIT

```sql
BEGIN;

INSERT INTO users (email)
VALUES ('user02@test.org');

SELECT * FROM users;

COMMIT;

SELECT * FROM users;
```

```text
BEGIN
 ↓
INSERT
 ↓
COMMIT
 ↓
DB에 영구 반영
```

이제 다시 조회해도 반영된 데이터를 확인할 수 있다.

---

## 2-3. SQL 실행 중 오류

```sql
BEGIN;

INSERT INTO users (email)
VALUES ('user03@test.org');

INSERT INTO users (id, email)
VALUES (1, 'user03@test.org');
```

발생한 오류:

```text
ERROR: 42804
column "id" is of type uuid
but expression is of type integer
```

`id` 컬럼이 `UUID` 타입인데 정수 `1`을 입력하려 했기 때문에 데이터 타입이 맞지 않아 오류가 발생했다.

---

## 2-4. ROLLBACK

```sql
BEGIN;

DELETE FROM users
WHERE email = 'user02@test.org';

SELECT * FROM users;

ROLLBACK;

SELECT * FROM users;
```

`COMMIT`하기 전이므로 `ROLLBACK`을 통해 DELETE 작업을 취소할 수 있다.

```text
DELETE
  ↓
아직 COMMIT 전
  ↓
ROLLBACK
  ↓
변경사항 취소
```

---

## 2-5. Transaction 없이 실행하면?

여러 작업을 하나의 Transaction으로 묶지 않고 각각 확정되도록 실행하면 앞의 작업이 이미 DB에 반영된 후 다음 작업에서 오류가 발생할 수 있다.

```text
작업 A
 ↓
DB 반영

작업 B
 ↓
ERROR ❌

결과
→ A만 DB에 남을 수 있음
→ 반쪽짜리 데이터 발생 가능
```

따라서 여러 DB 작업이 **하나의 작업처럼 함께 성공하거나 실패해야 한다면 Transaction으로 묶어서 처리**한다.

# 3. Supabase SDK

## 3-1. Supabase

**Supabase**는 PostgreSQL을 기반으로 Database뿐 아니라 Authentication, Storage, Realtime 등의 Backend 기능을 제공하는 플랫폼이다.

```text
Application
     ↓
Supabase
     │
     ├─ Database
     ├─ Authentication
     ├─ Storage
     └─ Realtime
```

---

## 3-2. SDK

**SDK(Software Development Kit)**는 특정 서비스의 기능을 프로그래밍 언어에서 쉽게 사용할 수 있도록 제공하는 **개발 도구 모음**이다.

현재 실습에서 작성하는 코드는 SQL 자체가 아니라:

> **Python + Supabase Python SDK**

이다.

```python
supabase.table("users").select("*").eq("id", 3).execute()
```

SQL로 생각하면 비슷한 의미는:

```sql
SELECT *
FROM users
WHERE id = 3;
```

전체적인 흐름:

```text
Python Code
     ↓
Supabase Python SDK
     ↓
Supabase API
     ↓
PostgreSQL
```

---

## 3-3. Method & Method Chaining

**Method(메서드)**는 객체를 통해 특정 작업을 수행하도록 호출하는 함수다.

```python
.table("users")    # users 테이블 지정
.select("*")       # 전체 컬럼 조회
.eq("id", 3)       # id = 3 조건
.execute()         # 요청 실행
```

메서드를 연속해서 연결하는 것을 **Method Chaining**이라고 한다.

```text
users 테이블에서
      ↓
전체 컬럼을 조회하는데
      ↓
id = 3인 데이터만
      ↓
실행
```

> `execute()`는 앞에서 구성한 요청을 **실제로 Supabase에 보내는 시점**이다.

# 4. Supabase 데이터 조회와 JOIN

## 4-1. 데이터 조회

Supabase Docs를 참고하여 Python SDK에서 데이터를 조회할 수 있다.

```python
response = (
    supabase.table("users")
        .select("*")
        .execute()
)

response.data
```

### SQL과 비교

SQL:

```sql
SELECT *
FROM users
WHERE id = 3;
```

Supabase SDK:

```python
response = (
    supabase.table("users")
        .select("*")
        .eq("id", 3)
        .execute()
)
```

대표적인 Filter:

| Supabase SDK | SQL 개념 |
|---|---|
| `.eq()` | `=` |
| `.ilike()` | `ILIKE` |
| `.in_()` | `IN` |
| `.is_()` | `IS` |

---

## 4-2. LEFT JOIN 형태

```python
response = (
    supabase.table("documents")
        .select("id, title, content, users(id, email)")
        .execute()
)

response.data
```

`documents`와 `users` 사이에 Foreign Key 관계가 설정되어 있다면 관련 사용자 데이터를 함께 조회할 수 있다.

```text
documents.user_id
        │
        │ FK
        ▼
users.id
```

---

## 4-3. INNER JOIN 형태

```python
response = (
    supabase.table("documents")
        .select("id, title, content, users!inner(id, email)")
        .ilike("users.email", "user%")
        .execute()
)

response.data
```

```text
users(...)        → 관련 데이터 포함 조회
users!inner(...)  → INNER JOIN 형태
```

# 5. Authentication & SSO

## 5-1. Login / Logout

로그인의 핵심은 서비스에서 **현재 사용자가 누구인지 식별하고 인증 상태를 유지하는 것**이다.

```text
LOGIN
  ↓
사용자 인증
  ↓
현재 사용자 식별
  ↓
사용자별 데이터 연결
  ↓
서비스 이용 상태 유지
```

**Logout**은 반대로 현재 사용자의 인증 세션을 종료하여 더 이상 로그인 상태로 식별되지 않도록 한다.

---

## 5-2. Authentication vs Authorization

- **Authentication(인증)** → "너 누구야?"
- **Authorization(인가)** → "너 이 데이터에 접근해도 돼?"

```text
Login
  ↓
Authentication
사용자 신원 확인
  ↓
Authorization
접근 권한 확인
  ↓
Data Access
```

`Confirm Email`을 끄는 것은 인증 전체를 없애는 것이 아니라 **이메일 소유 확인 단계를 실습 편의를 위해 생략**하는 것이다.

---

## 5-3. SSO

**SSO(Single Sign-On)**는 한 번의 로그인(인증)으로 여러 연결된 애플리케이션이나 서비스에 추가 로그인 없이 접근할 수 있도록 하는 통합 인증 방식이다.

```text
한 번 Login
    ↓
통합 인증
    ↓
┌────┼────┐
▼    ▼    ▼
App A App B App C
```

> **한 번 인증 → 여러 연결된 서비스 이용**

# 🛠️ PROBLEM SOLVING

## 1. `.single().execute()` APIError

### 문제

```text
PGRST116
The result contains 0 rows
```

### 원인

`.single()`은 조회 결과가 **정확히 1개**일 것을 기대하지만 실제 결과가 0개였다.

### 해결 및 확인

먼저 `.single()` 없이 실제 조회 결과를 확인한다.

```python
supabase.table("users") \
    .select("*") \
    .ilike("email", "user04%") \
    .execute()
```

결과가 0~1개일 수 있다면:

```python
.maybe_single()
```

을 고려할 수 있다.

> **실제 조회 결과 확인 → 조건 점검 → `.single()` 사용 여부 판단**

---

## 2. Table Relationship APIError

### 문제

```text
Could not find a relationship
between 'documents' and 'user'
```

기존 코드:

```python
.select("id, title, content, user(id, email)")
```

### 원인

Supabase가 `documents`와 `user` 사이의 Foreign Key 관계를 찾지 못했다.

실제 테이블이 `users`라면:

```python
.select("id, title, content, users(id, email)")
```

DB에서 실제 관계도 확인한다.

```text
documents.user_id
        │
        │ FK
        ▼
users.id
```

### Error 확인 포인트

```text
Method Chaining
      ↓
요청 구성
      ↓
execute()
      ↓
실제 요청 전송
      ↓
ERROR 발견
```

따라서 `execute()`가 오류 위치로 표시되더라도 `execute()` 자체가 문제라고 단정하지 않는다.

앞에서 작성한:

- 테이블명
- 컬럼명
- 조회 조건
- Filter
- Foreign Key 관계

등을 함께 확인한다.

> **에러가 발생한 줄뿐 아니라 `message`, `code`, `details`, `hint`를 확인한다.**
