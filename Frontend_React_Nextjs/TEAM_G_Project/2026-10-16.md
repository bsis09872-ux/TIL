## 1. 오늘 수행한 업무

### A. 소분판매·공동구매 시장조사 자료 공유

전날 준비한 소분판매 및 공동구매 관련 조사 내용을 팀원들과 공유했다.

**조사 목적**

초기 아이디어였던 소분판매·공동구매가 실제로 어떤 서비스 구조를 필요로 하는지 이해하고, 팀의 기획 방향을 재검토하기 위함이었다.

**조사 및 정리 내용**

- 1인 가구와 소량 식재료 구매 문제
- 소분판매·공동구매 관련 서비스 사례
- 실제 서비스에서 사용되는 용어
- 사회·문화적 배경과 소비자 관점
- 공동구매 운영 구조 및 구현 시 고려사항

**결과:** 팀의 서비스 방향 재검토를 위한 참고 자료로 공유했다.

### B. 서비스 구조 변경 논의 참여

팀원들의 조사 결과를 함께 검토하고, 초기 매거진형 큐레이션 중심 구조에서 소분 팟 신청·참여 중심 구조로 전환하는 논의에 참여했다.

이 과정에서 초기 기획과 실제 구현 방향 사이의 차이를 다시 생각하게 되었다.

### C. 중간발표 참관 및 타 팀 사례 분석

다른 팀의 발표를 들으며 다음 요소를 중점적으로 관찰했다.

- 기획 의도를 얼마나 간결하게 전달하는가?
- 팀원별 역할과 산출물이 명확하게 드러나는가?
- 구현 기술을 실제 화면과 연결하여 설명하는가?
- 트러블슈팅 과정과 해결 결과를 제시하는가?
- 실제 시연을 통해 구현 결과를 검증하는가?

특히 D조의 역할·트러블슈팅 중심 발표와 F조의 CSS Module 문제 해결 경험이 인상적이었다.

### D. 담당 페이지 및 개발 범위 확인

새로운 서비스 구조에 따라 개인 담당 페이지를 확인했다.

| 담당 페이지 | 주요 개발 대상 |
|---|---|
| AI 설문조사 | 설문 화면 및 사용자 입력 흐름 |
| 상품 상세 | 상품 정보와 소분 관련 정보 표시 |
| 팟 대기 | 모집 진행 상태와 참여 정보 표시 |
| 결제 | 결제 진행 화면 |
| 결제 완료 | 결제 결과 및 완료 안내 |

**현재 단계:** 담당 범위 확정 및 구현 준비. 실제 기능 완성 여부는 후속 작업에서 별도 기록한다.

## 2. 주요 문제와 의사결정 과정

### Problem 01. 협업을 위한 의견 수용이 핵심 기획의 우선순위를 약화시킨 문제

**상황**

초기 소분판매·공동구매 아이디어가 팀의 프로젝트 주제로 채택되었다.

하지만 팀원마다 서비스에 대해 중요하게 생각하는 요소가 달랐고, 짧은 기간 안에 원활한 협업 관계를 형성해야 했다.

**나의 접근**

나는 특정 의견을 일방적으로 관철하기보다, 팀원 간 불필요한 갈등을 줄이고 다양한 관점을 반영하는 것이 중요하다고 판단했다.

이에 팀원들이 제시한 큐레이션, 브랜드 스토리텔링, 디자인 관련 아이디어를 적극적으로 수용하고 보완하는 방식으로 논의에 참여했다.

**발견한 문제**

다양한 의견을 수용하는 과정에서 아이디어의 확장과 핵심 기능의 우선순위를 충분히 구분하지 못했다.

결과적으로 매거진형 큐레이션이 서비스 전면에 배치되고, 소분판매·공동구매라는 본래 핵심 기능은 사용자 흐름의 후반부로 밀려났다.

**해결 접근**

- 초기 문제 정의를 다시 검토했다.
- 소분판매·공동구매에 관한 조사 자료를 준비하고 공유했다.
- 팀원들과 함께 기존 기획의 한계를 논의했다.
- 핵심 사용자 행동을 중심으로 서비스를 재설계하는 방향에 참여했다.

**결과**

팀은 매거진형 큐레이션 구조를 제외하고, 소분 팟 신청·참여를 중심으로 사용자 흐름을 변경했다.

**배운 점**

다양한 의견을 존중하는 것과 모든 의견을 동일한 우선순위로 반영하는 것은 다르다.

협업에서 중요한 것은 단순히 의견 충돌을 줄이는 것이 아니라, 공통의 목표와 판단 기준을 바탕으로 합의를 형성하는 것이다.

### Problem 02. 구현 가능한 MVP와 핵심 서비스 가치의 불일치

**상황**

초기에는 개발 일정을 고려해 구현 가능한 큐레이션 기반 상품 탐색·판매 흐름부터 제작하기로 했다.

그러나 실제 구현 과정에서 해당 구조가 초기 문제 정의를 충분히 반영하지 못한다는 한계를 발견했다.

**원인 분석**

- 구현하기 쉬운 화면을 먼저 고려함
- 소분 팟의 비즈니스 로직이 충분히 정의되지 않음
- 데이터 구조와 사용자 흐름에 대한 리서치 부족
- 핵심 기능과 부가 기능의 우선순위 불명확

**해결 접근**

사용자의 핵심 행동을 기준으로 서비스 흐름을 재검토했다.

기존 매거진형 구조 대신 상품 탐색부터 소분 팟 참여, 대기, 결제까지 연결되는 흐름을 중심으로 화면을 구성하기로 했다.

**변경된 흐름**

메인 → 상품 목록·상세 → 팟 신청·참여 → 대기 → 결제 안내 → 결제 → 완료

**배운 점**

MVP는 단순히 구현하기 쉬운 기능의 집합이 아니라, **서비스가 해결하려는 핵심 문제를 검증할 수 있는 최소한의 기능**이어야 한다.

### Problem 03. 협업 과정에서 작업 단위와 책임 범위가 불명확한 문제

**상황**

기획과 구현을 병행하면서 기능의 범위, 담당 페이지, 공통 컴포넌트 작업이 명확하게 구분되지 않으면 일정 지연이나 중복 작업이 발생할 수 있다는 점을 확인했다.

**해결 접근**

팀 회의와 튜터 피드백을 바탕으로 다음 방향을 정리했다.

- 페이지 및 기능별 담당자 명확화
- 컴포넌트 단위로 업무 세분화
- 작은 단위의 PR 작성 및 코드 리뷰
- 작업 결과와 문제 해결 과정 문서화
- 구현 우선순위와 일정 공유

**배운 점**

업무 분담은 단순히 페이지를 나누는 것이 아니라, 각 작업의 범위와 완료 기준을 명확히 하는 과정이다.

## 3. 새롭게 학습한 개발·프로젝트 개념

| 개념 | 학습 내용 |
|---|---|
| MVP (Minimum Viable Product) | 핵심 사용자 문제를 검증하기 위한 최소 기능 제품 |
| User Flow | 사용자가 목표를 달성하기 위해 이동하는 화면과 행동의 흐름 |
| User Action | 클릭, 신청, 취소, 결제 등 사용자가 수행하는 개별 행동 |
| Funnel | 사용자가 탐색부터 목표 행동까지 진행하는 단계별 전환 구조 |
| Business Logic | 참여 조건, 모집 완료, 결제 가능 여부 등 서비스 운영 규칙 |
| IA (Information Architecture) | 페이지와 정보의 분류 및 연결 구조 |
| SSR (Server-Side Rendering) | 서버에서 HTML을 생성하는 렌더링 방식 |
| CSR (Client-Side Rendering) | 브라우저에서 JavaScript를 실행해 화면을 렌더링하는 방식 |
| PR (Pull Request) | 코드 변경 사항에 대한 검토와 병합을 요청하는 작업 |
| Troubleshooting | 문제를 재현·분석하고 해결 과정을 검증하는 활동 |

### 추가로 학습이 필요한 내용

- React Server Component와 Client Component의 구분
- Next.js에서 SSR·CSR과 컴포넌트 실행 위치의 관계
- 소분 팟의 상태 변화와 프론트엔드 상태 관리
- 결제 조건 충족에 따른 UI 분기
- 공통 컴포넌트와 페이지별 컴포넌트의 설계 기준

## 4. 다른 팀 발표에서 얻은 인사이트

### A. 역할과 결과물을 연결하는 발표

D조는 팀원별 담당 업무와 산출물을 구체적으로 소개하고, 실제 시연 및 트러블슈팅을 공유했다.

→ 최종발표에서 나 역시 담당 페이지, 사용 기술, 해결한 문제, 결과물을 연결하여 설명할 필요가 있다.

### B. UI 단순화와 정보 접근성의 균형

E조는 상품 목록에서 상품명과 가격을 기본적으로 숨기고 호버 시 노출하는 방식을 제안했다.

개인적으로는 시각적 단순화에는 도움이 될 수 있지만, 가격 비교가 어려워지는 새로운 문제가 발생할 수 있다고 생각했다.

대안으로 찜 목록에서 동일 카테고리 상품을 모아 보여주고 가격 정보를 노출하는 방법을 고려했다.

→ UX 개선은 단순히 요소를 줄이는 것이 아니라, 사용자의 주요 행동에 필요한 정보가 유지되는지 함께 판단해야 한다.

### C. CSS 문제의 원인 추적

F조는 CSS Module 관련 문제를 소개하며 증상이 나타나는 위치와 실제 원인이 있는 위치가 다를 수 있다고 설명했다.

→ 오류가 발생했을 때 해당 컴포넌트만 수정하기보다 상위 레이아웃, 스타일 적용 범위, 컴포넌트 간 관계도 확인해야 한다.

### D. 기술 중심의 결과 설명

A조의 애니메이션과 호버 영상, B조의 테스트 결제, C조의 페이지별 기술 설명을 통해 구현 결과를 구체적으로 보여주는 발표의 중요성을 확인했다.

## 5. 오늘의 회고

오늘은 코드를 얼마나 작성했는가보다 **무엇을 구현해야 하는지, 왜 그 기능을 구현해야 하는지**를 다시 생각하게 된 날이었다.

처음에는 팀원들의 다양한 의견을 수용하는 것이 원활한 협업을 위한 최선의 접근이라고 생각했다. 그러나 의견을 폭넓게 반영하는 과정에서 핵심 서비스의 방향이 흐려질 수 있다는 점을 경험했다.

이번 구조 변경을 통해 팀워크를 유지하는 것과 프로젝트 목표를 명확하게 관리하는 것이 함께 필요하다는 사실을 배웠다.

앞으로는 팀원들의 의견을 존중하면서도 다음 네 가지 기준을 바탕으로 판단하고자 한다.

1. 해결하려는 사용자 문제가 무엇인가?
2. 해당 기능이 핵심 사용자 행동에 기여하는가?
3. 현재 일정과 기술 수준에서 구현 가능한가?
4. 구현 결과를 어떤 방식으로 확인하고 검증할 수 있는가?

**오늘의 결론:** 좋은 협업은 모든 의견을 수용하는 것이 아니라, 서로 다른 의견을 공동의 목표에 맞게 조율하는 과정이다.
