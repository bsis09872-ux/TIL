# GitHub 협업 흐름과 Git 복습

> 📅 2026.08.05

오늘은 Git의 주요 명령어를 복습하고, GitHub의 Issue, Project, Pull Request를 활용해 팀 협업 워크플로우를 직접 체험했다.

## Git 핵심 복습

### 마지막 Commit 메시지 수정

가장 최근 Commit의 메시지를 수정할 때 사용한다.

```bash
git commit --amend -m "수정할 커밋 메시지"
```

### Reset과 Revert

두 명령어 모두 변경 사항을 되돌릴 때 사용하지만 기록을 처리하는 방식이 다르다.

| 명령어 | 특징 |
|---|---|
| `git reset` | 브랜치를 이전 시점으로 이동하며 이후 기록을 제거하거나 보이지 않게 할 수 있음 |
| `git revert` | 기존 기록을 유지하고 변경을 취소하는 새로운 Commit을 추가함 |

아직 원격 저장소에 공유하지 않은 기록은 `reset`, 이미 협업자와 공유한 기록은 `revert`를 사용하는 것이 비교적 안전하다.

### Branch

Branch는 다른 작업과의 간섭을 줄이고 기능별로 독립해서 개발하기 위한 작업 공간이다. 기능 Branch에서 작업한 뒤 완성된 내용을 `main` 또는 개발 Branch에 병합한다.

### Merge와 Rebase

`merge`는 서로 다른 Branch의 작업 이력을 통합한다.

- **Fast-forward Merge**: 현재 Branch에 별도 변경이 없다면 Branch 포인터만 앞으로 이동한다.
- **3-Way Merge**: 두 Branch가 각각 변경되었다면 공통 조상을 기준으로 통합하고 Merge Commit을 만든다.
- 같은 파일의 같은 부분을 여러 Branch에서 수정하면 Conflict가 발생할 가능성이 커진다.

`rebase`는 분기된 Branch의 Commit을 최신 `main` 위에 다시 적용해 Commit 기록을 선형으로 정리한다.

```bash
git rebase main
```

Conflict를 해결했다면 파일을 Staging Area에 올린 뒤 계속 진행한다.

```bash
git add 파일명
git rebase --continue
```

현재 Commit을 건너뛰거나 Rebase 전체를 중단할 수도 있다.

```bash
git rebase --skip
git rebase --abort
```

### 원격 저장소 연결

로컬 저장소와 GitHub 원격 저장소를 연결한다.

```bash
git remote add origin <원격-저장소-주소>
git remote -v
```

GitHub의 변경 내용을 가져오면서 내 로컬 Commit을 그 위에 다시 적용하려면 다음 명령어를 사용할 수 있다.

```bash
git pull --rebase origin main
```

## GitHub 협업 기능

- **SourceTree**: Git 명령을 GUI로 사용할 수 있는 도구이다. 이번에는 오류로 인해 화면과 기능만 확인했다.
- **Rulesets**: `main`과 같은 중요 Branch를 보호하고 직접 Push나 병합 조건을 제한한다.
- **Collaborators**: 저장소에 협업자를 초대한다.
- **Fork**: 다른 사람의 저장소를 내 GitHub 계정으로 복제해 독립적으로 작업한다.
- **`.gitignore`**: Git이 추적하지 않을 파일이나 폴더를 지정한다.
- **`.github`**: Issue 및 Pull Request 템플릿 등 GitHub 설정 파일을 관리한다.
- **Projects**: Kanban 보드에서 Issue와 작업 진행 상태를 관리한다.
- **Pull Request**: 기능 Branch의 작업을 검토받고 다른 Branch에 병합하도록 요청한다.

Issue는 가능한 한 **하나의 작업 단위**로 작성한다.

Commit 메시지에서 Issue를 참조할 수 있다.

```bash
git commit -m "feat: 로그인 기능 구현 (#12)"
```

PR 본문에서 아래 키워드를 사용하면 PR이 Merge될 때 연결된 Issue를 자동으로 닫을 수 있다.

```text
Closes #12
Fixes #15
Resolves #8
```

## 오늘의 실습: GitHub 협업 워크플로우

실제 코드를 구현하는 대신 Markdown 파일을 작성하며 GitHub 협업의 전체 흐름을 경험했다.

1. **프로젝트 주제 선정**
   - 쇼핑몰 서비스를 주제로 정했다.

2. **GitHub 협업 저장소 생성**
   - 팀원이 GitHub에 `project01` 저장소를 생성했다.
   - Collaborators에 팀원들을 초대했다.

3. **로컬 작업 환경 구성**
   - 각자 `Documents` 폴더에 `project01` 작업 폴더를 만들었다.
   - 로컬 Git 저장소를 초기화하고 원격 저장소를 연결했다.

```bash
cd Documents
cd project01
git init
git remote add origin <GitHub-저장소-주소>
git remote -v
```

4. **협업 규칙 수립**
   - 회의를 통해 Branch 이름, Commit 메시지, Issue 및 PR 작성 규칙을 정했다.
   - 정한 내용을 `CONTRIBUTING.md`에 작성하기로 했다.

5. **서비스 기능 흐름 설계**
   - 회원가입 → 로그인 → 상품 검색 → 상품 상세 → 장바구니 → 결제 순서로 사용자 흐름을 구성했다.
   - 처음 구상한 기능을 그대로 사용하지 않고 **MVP 기준으로 최소 기능을 다시 선정**했다.

6. **담당 기능 분배**
   - PAYMENT: 배서인
   - MEMBER: 배유민
   - ORDER: 변기국
   - PRODUCT: 서상혁

7. **프로젝트 기본 문서 작성**
   - 프로젝트 설명과 역할 분담 내용을 `README.md`에 작성했다.
   - 협업에 필요한 템플릿을 생성했다.

```text
.github/
├── ISSUE_TEMPLATE.md
├── ISSUE_TEMPLATE_FOR_BUG.md
└── PULL_REQUEST_TEMPLATE.md
```

작성한 파일을 Commit한 뒤 원격 저장소에 Push했다.

```bash
git add .
git commit -m "docs: 협업 문서 및 템플릿 추가"
git push origin main
```

8. **GitHub Project와 Issue 생성**
   - GitHub Projects에서 Kanban 템플릿을 생성했다.
   - 기능별 Issue를 만들고 담당자와 프로젝트를 연결했다.
   - **Issue 1개를 작업 1개 단위**로 관리했다.

9. **Branch 보호 설정**
   - 기본 문서와 초기 설정이 완료된 후 `main` Branch에 Ruleset을 적용했다.
   - 이후 작업은 `main`에 직접 Push하지 않고 Pull Request를 거치도록 했다.

10. **기능 Branch에서 작업**
    - 각자 맡은 기능에 맞는 Branch를 생성하고 이동했다.

```bash
git switch -c feature/payment
```

실제 코드 대신 담당 기능을 설명하는 Markdown 파일을 작성하고 기능 단위로 Commit했다.

```bash
git status
git add PAYMENT.md
git commit -m "feat: 결제 기능 문서 작성"
```

11. **기능 Branch를 원격 저장소에 Push**

```bash
git push -u origin feature/payment
```

12. **Pull Request 생성**
    - `feature/payment`에서 `main`으로 병합하는 Pull Request를 작성했다.
    - PR 본문에 작업 내용과 연결된 Issue를 작성했다.

```text
Closes #12
```

13. **리뷰와 병합**
    - 팀원이 Comment를 작성하고 변경 사항을 검토했다.
    - Approve 후 Pull Request를 Merge했다.
    - Merge된 PR과 연결된 Issue가 자동으로 완료되도록 설정했다.
    - GitHub Project의 작업 카드도 완료 상태로 이동시켰다.

## 오늘 이해한 내용

GitHub 협업은 단순히 파일을 Push하는 작업이 아니라 다음 흐름으로 진행된다.

```text
Issue 생성
→ 기능 Branch 생성
→ 기능 작업 및 Commit
→ 기능 Branch Push
→ Pull Request 작성
→ 리뷰와 승인
→ Merge
→ Issue 및 Project 완료
```

특히 `main`에 직접 작업하지 않고 기능별 Branch와 Pull Request를 사용하면 작업 이력과 담당 범위가 명확해지고, 팀원의 작업에 미치는 영향을 줄일 수 있다는 점을 실습을 통해 확인했다.
