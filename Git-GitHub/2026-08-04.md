# 😎 오늘의 질의응답

## 1. `git add`를 했는데 `git log`에 나타나지 않는 이유

`git add`는 변경 사항을 **Staging Area에 등록하는 명령어**이다.

`git log`는 **Commit이 완료된 기록만 보여주기 때문에**, `git add`만 실행한 상태에서는 새로운 기록이 나타나지 않는다.

```bash
git status
git diff --staged
git commit -m "커밋 메시지"
git log
```

현재 작업 중인 저장소가 맞는지도 확인해야 한다.

```bash
cd <디렉터리>
git status
```

정리하면 다음과 같다.

```text
git add
→ Commit 후보로 등록

git commit
→ Repository에 버전 기록

git log
→ 기록된 Commit 확인
```

---

## 2. `HEAD`와 `main`의 차이는 무엇인가?

- **main**: 브랜치의 이름
- **HEAD**: 현재 내가 보고 있거나 작업 중인 위치를 가리키는 포인터

보통 `main` 브랜치에서 작업 중이라면 다음과 같은 관계가 된다.

```text
HEAD → main → 최신 Commit
```

다른 브랜치로 이동하면 `HEAD`도 해당 브랜치를 가리키게 된다.

```bash
git switch feature/login
```

```text
HEAD → feature/login → 최신 Commit
```

---

## 3. `HEAD`의 위치는 어떻게 바꿀까?

브랜치를 이동하면 `HEAD`의 위치도 함께 바뀐다.

```bash
git switch 브랜치명
```

또는 특정 Commit 상태를 확인할 수 있다.

```bash
git checkout <commit-id>
```

특정 Commit으로 직접 이동하면 브랜치가 아닌 Commit 자체를 가리키는 **Detached HEAD 상태**가 될 수 있으므로 주의해야 한다.

---

## 4. `-`와 `--`의 차이

일반적으로 다음과 같이 사용된다.

- `-`: 짧은 옵션
- `--`: 긴 옵션

예시:

```bash
git branch -d feature/login
git reset --hard HEAD~1
```

다만 Git 명령어마다 지원하는 옵션이 다르므로 항상 같은 의미로 대응되는 것은 아니다.

```bash
git help <명령어>
```

를 통해 정확한 옵션을 확인할 수 있다.

# 📚 오늘 배운 내용

## 1. Staging과 Commit의 작업 흐름

Git의 기본 흐름은 다음과 같다.

```text
현재 파일 상태 확인
        ↓
변경 사항을 Staging Area에 등록
        ↓
확정된 내용을 Repository에 기록
```

```bash
git status
git add 파일명
git diff --staged
git commit -m "커밋 메시지"
```

`git add`나 `git commit` 전에 항상 `git status`를 확인하는 습관을 들이는 것이 좋다.

---

## 2. 부분적으로 Staging하기

파일 전체가 아니라 변경된 내용 중 일부만 Staging Area에 올릴 수 있다.

```bash
git add -p
```

하나의 파일 안에서 여러 기능을 수정했지만, 기능별로 Commit을 나누고 싶을 때 유용하다.

---

## 3. 기능 단위 Commit

Commit은 파일 단위보다는 **기능 단위**로 나누어 기록하는 것이 좋다.

예시:

```text
feat: 로그인 기능 추가
fix: 로그인 오류 수정
docs: README 수정
```

### Commit Message Convention

| 접두어 | 의미 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `refactor` | 기능 변화 없이 코드 구조 개선 |
| `chore` | 설정, 빌드 등 기타 작업 |
| `test` | 테스트 코드 추가 및 수정 |

---

## 4. Commit 되돌리기

### `git reset`

현재 브랜치가 가리키는 위치를 특정 Commit으로 이동시키고, 옵션에 따라 Staging Area와 Working Directory도 함께 변경한다.

#### `--soft`

```bash
git reset --soft HEAD~1
```

- Commit 취소
- Staging Area 유지
- Working Directory 유지

#### `--mixed`

```bash
git reset --mixed HEAD~1
```

- Commit 취소
- Staging Area 초기화
- Working Directory 유지
- 기본 옵션

#### `--hard`

```bash
git reset --hard HEAD~1
```

- 현재 브랜치를 이전 Commit으로 이동
- Staging Area를 해당 Commit 상태로 초기화
- Working Directory도 해당 Commit 상태로 덮어씀

추적 중인 변경 사항이 사라질 수 있으므로 가장 주의해야 하는 옵션이다.

---

### `git revert`

```bash
git revert <commit-id>
```

기존 Commit을 삭제하지 않고, 해당 변경을 반대로 적용하는 **새로운 Commit**을 만든다.

이미 GitHub에 Push하여 다른 사람과 공유된 Commit을 안전하게 취소할 때 사용한다.

```text
A → B → C → D

D = C의 변경을 취소하는 새로운 Commit
```

---

## 5. `reset`과 `revert`의 차이

| 구분 | `reset` | `revert` |
|---|---|---|
| 기존 이력 | 변경하거나 제거할 수 있음 | 그대로 유지 |
| 취소 방식 | 브랜치 위치를 이전으로 이동 | 반대 변경을 새 Commit으로 생성 |
| 주요 사용처 | 아직 공유하지 않은 로컬 실수 | 이미 Push한 Commit 취소 |
| 협업 안전성 | 주의 필요 | 비교적 안전 |

---

## 6. `git reflog`

```bash
git reflog
```

`reflog`는 로컬 저장소에서 `HEAD`와 브랜치 등의 참조가 어떤 Commit을 가리켰는지 기록한다.

`reset`이나 `rebase`로 Commit이 보이지 않게 되었더라도, 해당 기록과 객체가 남아 있다면 복구할 수 있다.

```bash
git reflog
git reset --hard HEAD@{1}
```

단, 다음 항목은 복구가 어렵거나 불가능할 수 있다.

- Git이 추적하지 않던 파일
- 아직 Commit하지 않은 변경 사항
- `git clean`으로 삭제한 파일
- Git 내부 정리 과정에서 제거된 객체

따라서 `reflog`는 강력한 복구 수단이지만 영구 백업은 아니다.

---

## 7. `HEAD~n`과 `HEAD@{n}`의 차이

### `HEAD~n`

현재 Commit에서 부모 Commit을 따라 `n`단계 이전 Commit을 가리킨다.

```bash
HEAD~1
HEAD~2
```

### `HEAD@{n}`

`reflog`를 기준으로 `HEAD`가 `n`번 이동하기 전에 가리켰던 위치를 뜻한다.

```bash
HEAD@{1}
HEAD@{2}
```

```text
HEAD~2
→ Commit 관계를 따라 두 단계 이전

HEAD@{2}
→ HEAD 이동 기록상 두 번 이전
```

## 8. Branch

Branch는 독립적으로 작업할 수 있는 공간이다.

기능별로 Branch를 나누면 다른 기능 개발에 영향을 주지 않고 작업할 수 있다.

### Branch 생성

```bash
git branch feature/login
```

### Branch 생성과 동시에 이동

```bash
git switch -c feature/login
```

또는

```bash
git checkout -b feature/login
```

### Branch 이동

```bash
git switch feature/login
```

### Branch 이름 예시

```text
feature/login
fix/login-error
hotfix/payment
docs/readme
test/user-api
release/v1.0
```

## 9. Branch 삭제와 이름 변경

### 삭제

```bash
git branch -d feature/login
```

강제 삭제:

```bash
git branch -D feature/login
```

### 현재 Branch 이름 변경

```bash
git branch -m 새이름
```

강제 변경:

```bash
git branch -M 새이름
```

## 10. Merge

```bash
git switch main
git merge feature/login
```

현재 브랜치에 다른 브랜치의 개발 이력을 통합한다.

### Fast-forward Merge

현재 브랜치가 따로 변경되지 않았고, 병합할 브랜치가 그대로 이어지는 경우 새로운 Merge Commit 없이 브랜치 포인터만 이동한다.

```text
A ─ B ─ C
        ↑
     feature
```

`main`이 `C`로 이동하며 병합된다.

### 3-Way Merge

두 브랜치가 각각 다른 Commit을 가진 경우 공통 조상을 기준으로 변경 사항을 통합하고 새로운 Merge Commit을 생성한다.

```text
      C ─ D
     /     \
A ─ B ───── M
```

`M`은 Merge Commit이다.

---

## 11. Merge Conflict

같은 파일의 같은 부분을 두 브랜치에서 서로 다르게 수정하면 Git이 어떤 내용을 선택해야 할지 판단하지 못해 Conflict가 발생한다.

충돌 파일을 직접 수정한 뒤 다음과 같이 완료한다.

```bash
git add 파일명
git merge --continue
```

또는:

```bash
git commit
```

병합 전체를 취소하려면:

```bash
git merge --abort
```

---

## 12. Rebase

Rebase는 현재 브랜치의 Commit을 새로운 기준점 위에 다시 적용하는 작업이다.

```bash
git switch feature/login
git rebase main
```

예시:

```text
      D ─ E  feature
     /
A ─ B ─ C    main
```

Rebase 이후:

```text
A ─ B ─ C ─ D' ─ E'
```

`D'`, `E'`는 새롭게 생성된 Commit이므로 기존 Commit과 Hash가 다르다.

### Rebase를 사용하는 이유

- 개인 브랜치를 최신 `main` 기준으로 정리
- Commit History를 직선 형태로 유지
- Merge 전에 최신 변경 사항 반영

### Rebase Conflict 해결

충돌을 수정한 뒤:

```bash
git add 파일명
git rebase --continue
```

현재 Commit을 건너뛰려면:

```bash
git rebase --skip
```

전체 작업을 취소하려면:

```bash
git rebase --abort
```

### 주의 사항

다른 사람이 이미 내려받아 작업 중인 공유 브랜치의 Commit History는 함부로 Rebase하지 않는다.

Rebase는 기존 Commit Hash를 바꾸므로 협업자의 History와 충돌할 수 있다.

---

## 13. Merge와 Rebase의 차이

| Merge | Rebase |
|---|---|
| 두 개발 이력을 통합 | Commit을 새 기준 위에 다시 적용 |
| Merge Commit 생성 가능 | Merge Commit 없이 직선 이력 생성 |
| 기존 Commit Hash 유지 | Commit Hash 변경 |
| 공유 브랜치에서도 비교적 안전 | 개인 브랜치에 권장 |
| 실제 분기 이력 유지 | History가 단순해짐 |

## 14. Stash

Commit하지 않은 작업을 잠시 임시 저장할 수 있다.

```bash
git stash
```

목록 확인:

```bash
git stash list
```

가장 최근 작업을 복원하고 목록에서 제거:

```bash
git stash pop
```

Branch를 이동하기 전에 변경 사항 때문에 이동이 막히거나, 아직 Commit하기 어려운 작업을 잠시 보관할 때 사용한다.

Branch 이동 전에 반드시 Commit해야 하는 것은 아니지만, 변경 사항을 안전하게 관리하기 위해 Commit 또는 Stash를 사용하는 것이 좋다.

## 15. 원격 저장소

원격 저장소는 로컬 저장소와 별도로 인터넷상에 존재하는 Git 저장소이다.

GitHub는 대표적인 원격 저장소 서비스이다.

### 원격 저장소 연결

```bash
git remote add origin <저장소-주소>
```

연결 확인:

```bash
git remote -v
```

주소 변경:

```bash
git remote set-url origin <새로운-주소>
```

---

## 16. Push와 Pull

### 로컬에서 원격으로 반영

```bash
git push origin main
```

최초 연결 시:

```bash
git push -u origin main
```

`-u` 옵션으로 현재 로컬 브랜치와 원격 브랜치의 추적 관계를 설정하면 이후에는 다음처럼 사용할 수 있다.

```bash
git push
```

### 원격에서 로컬로 반영

```bash
git pull origin main
```

`git pull`은 원격 변경 내용을 가져오고 현재 브랜치에 통합한다.

# 💻 실습

```bash
git status
git add -p
git diff --staged
git commit -m "feat: 기능 추가"

git switch -c feature/login
git switch main
git merge feature/login

git reflog
git stash
git stash list
git stash pop

git remote add origin <저장소-주소>
git push -u origin main
```

### 실행 결과

- 현재 파일과 Staging Area의 상태를 확인했다.
- 변경 사항을 부분적으로 Staging Area에 등록했다.
- 기능별 Commit을 작성했다.
- Branch를 만들고 이동한 뒤 Merge를 실습했다.
- `reflog`를 통해 `HEAD` 이동 기록을 확인했다.
- Commit하지 않은 작업을 `stash`에 임시 저장했다.
- 로컬 저장소와 GitHub 원격 저장소를 연결했다.

# 💡 오늘 이해한 내용

오늘 가장 중요하게 이해한 것은 **Commit History를 유지할지 변경할지에 따라 명령어를 선택해야 한다는 점**이다.

`reset`은 현재 브랜치의 위치를 이전 Commit으로 옮기기 때문에 아직 공유하지 않은 로컬 작업을 수정할 때 적합하다.

반면 `revert`는 기존 이력을 남긴 채 변경을 취소하는 새로운 Commit을 만들기 때문에 이미 Push한 기록을 되돌릴 때 더 안전하다.

또한 `merge`는 두 브랜치의 개발 이력을 통합하고, `rebase`는 내 Commit을 최신 기준 위에 다시 적용한다는 차이를 이해했다.

Branch는 단순히 Commit을 나누는 기능이 아니라, 서로의 작업을 방해하지 않도록 독립된 작업 공간을 제공하는 기능이다.
