# 😎 오늘의 질의응답

## 1. `git add`를 했는데 `git log`에 나타나지 않는 이유

`git add`는 변경 사항을 **Staging Area에 올리는 명령어**이고, `git log`는 **Commit된 기록만 보여준다.**

```bash
git status
git diff --staged
git commit -m "커밋 메시지"
git log
```

현재 올바른 저장소에서 작업 중인지도 확인한다.

```bash
cd <디렉터리>
git status
```

---

## 2. `HEAD`와 `main`의 차이

- `main`: 브랜치 이름
- `HEAD`: 현재 작업 중인 위치를 가리키는 포인터

```text
HEAD → main → 최신 Commit
```

다른 브랜치로 이동하면 `HEAD`도 함께 이동한다.

```bash
git switch feature/login
```

```text
HEAD → feature/login → 최신 Commit
```

---

## 3. `-`와 `--`의 차이

일반적으로 다음과 같이 사용한다.

- `-`: 짧은 옵션
- `--`: 긴 옵션

```bash
git branch -d feature/login
git reset --hard HEAD~1
```

명령어마다 지원하는 옵션은 다르므로 다음 명령어로 확인할 수 있다.

```bash
git help <명령어>
```

# 📚 오늘 배운 내용

## 1. Staging과 Commit 흐름

```text
Working Directory
        ↓ git add
Staging Area
        ↓ git commit
Repository
```

```bash
git status
git add 파일명
git diff --staged
git commit -m "커밋 메시지"
```

`git add`와 `git commit` 전에는 `git status`를 확인하는 습관을 들인다.

---

## 2. 변경 사항 비교

| 명령어 | 비교 대상 | 확인 내용 |
|---|---|---|
| `git diff` | Working Directory ↔ Staging Area | 아직 `git add`하지 않은 변경 |
| `git diff --staged` | Staging Area ↔ HEAD | 다음 Commit에 포함될 변경 |
| `git diff HEAD` | Working Directory ↔ HEAD | 마지막 Commit 이후 전체 변경 |

```bash
git diff
git diff --staged
git diff HEAD
```

---

## 3. 부분적으로 Staging하기

```bash
git add -p
```

한 파일 안의 변경 사항을 일부만 Staging Area에 올릴 수 있다. 여러 기능을 수정했을 때 기능별로 Commit을 나누는 데 유용하다.

---

## 4. Commit Message Convention

Commit은 파일 단위보다 **기능 단위**로 기록한다.

| 접두어 | 의미 |
|---|---|
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `refactor` | 기능 변화 없는 코드 개선 |
| `chore` | 설정 및 기타 작업 |
| `test` | 테스트 추가 및 수정 |

```text
feat: 로그인 기능 추가
fix: 로그인 오류 수정
docs: README 수정
```

# 🔄 변경 사항 되돌리기

## 5. `git reset`

현재 브랜치를 이전 Commit으로 이동하며, 옵션에 따라 Staging Area와 Working Directory도 변경한다.

### `--soft`

```bash
git reset --soft HEAD~1
```

- Commit 취소
- Staging Area 유지
- Working Directory 유지

### `--mixed`

```bash
git reset --mixed HEAD~1
```

- Commit 취소
- Staging Area 초기화
- Working Directory 유지
- 기본 옵션

### `--hard`

```bash
git reset --hard HEAD~1
```

- Commit 위치 이동
- Staging Area 초기화
- Working Directory를 해당 Commit 상태로 변경

추적 중인 변경 사항이 사라질 수 있어 주의해야 한다.

---

## 6. `git revert`

```bash
git revert <commit-id>
```

기존 Commit을 삭제하지 않고, 해당 변경을 취소하는 **새로운 Commit**을 만든다.

이미 원격 저장소에 Push한 Commit을 취소할 때 주로 사용한다.

---

## 7. Reset과 Revert 비교

| `reset` | `revert` |
|---|---|
| 기존 이력을 변경할 수 있음 | 기존 이력을 유지 |
| 브랜치 위치를 이전으로 이동 | 취소 내용을 새 Commit으로 기록 |
| Push 전 로컬 실수 수정에 적합 | Push 후 협업 기록 취소에 적합 |

---

## 8. `git reflog`

```bash
git reflog
```

`HEAD`와 브랜치가 이동한 기록을 확인한다.

`reset`이나 `rebase` 후 Commit이 보이지 않을 때 이전 위치를 찾는 데 사용할 수 있다.

```bash
git reflog
git reset --hard HEAD@{1}
```

단, `reflog`는 로컬 기록이며 영구 백업은 아니다.

---

## 9. `HEAD~n`과 `HEAD@{n}`

```text
HEAD~2
→ Commit 관계를 따라 두 단계 이전

HEAD@{2}
→ HEAD 이동 기록상 두 번 이전
```

# 🌿 Branch와 병합

## 10. Branch

Branch는 기능별로 독립해서 작업할 수 있도록 만든 작업 흐름이다.

### 생성

```bash
git branch feature/login
```

### 생성과 동시에 이동

```bash
git switch -c feature/login
```

또는

```bash
git checkout -b feature/login
```

### 이동

```bash
git switch feature/login
```

### 삭제

```bash
git branch -d feature/login
```

강제 삭제:

```bash
git branch -D feature/login
```

### 이름 변경

```bash
git branch -m 새이름
```

---

## 11. Merge

현재 브랜치에 다른 브랜치의 작업 내용을 통합한다.

```bash
git switch main
git merge feature/login
```

### Fast-forward Merge

현재 브랜치에 별도 변경이 없다면 새로운 Merge Commit 없이 브랜치 위치만 앞으로 이동한다.

### 3-Way Merge

두 브랜치가 각각 변경되었다면 공통 조상을 기준으로 병합하고 Merge Commit을 만든다.

---

## 12. Merge Conflict

같은 파일의 같은 부분을 서로 다르게 수정하면 Conflict가 발생한다.

충돌 내용을 직접 수정한 후:

```bash
git add 파일명
git merge --continue
```

또는:

```bash
git commit
```

병합을 취소하려면:

```bash
git merge --abort
```

---

## 13. Rebase

현재 브랜치의 Commit을 새로운 기준점 위에 다시 적용한다.

```bash
git switch feature/login
git rebase main
```

```text
기존
A ─ B ─ C
     └─ D ─ E

Rebase 후
A ─ B ─ C ─ D' ─ E'
```

`D'`, `E'`는 새로 생성된 Commit이므로 Hash도 변경된다.

충돌 해결 후:

```bash
git add 파일명
git rebase --continue
```

취소:

```bash
git rebase --abort
```

다른 사람이 함께 사용하는 공유 브랜치의 History는 함부로 Rebase하지 않는다.

---

## 14. Merge와 Rebase 비교

| Merge | Rebase |
|---|---|
| 두 개발 이력을 합침 | Commit을 새 기준 위에 다시 적용 |
| 기존 이력 유지 | Commit Hash 변경 |
| Merge Commit이 생길 수 있음 | 직선형 History 생성 |
| 협업 브랜치에 비교적 안전 | 개인 브랜치 정리에 적합 |

---

## 15. Stash

Commit하지 않은 작업을 잠시 보관한다.

```bash
git stash
git stash list
git stash pop
```

Branch를 이동하기 전에 작업을 Commit하기 어렵다면 임시 저장소처럼 사용할 수 있다.

# ☁️ GitHub와 원격 저장소

## 16. 원격 저장소

원격 저장소는 로컬 저장소와 별도로 인터넷상에 존재하는 Git 저장소이다.

GitHub는 대표적인 원격 저장소 서비스이다.

### 연결

```bash
git remote add origin <저장소-주소>
```

### 확인

```bash
git remote -v
```

### 주소 변경

```bash
git remote set-url origin <새로운-주소>
```

---

## 17. `git clone`

```bash
git clone <저장소-주소>
```

원격 저장소의 프로젝트를 내 컴퓨터에 처음 복제하는 명령어이다.

파일뿐 아니라 Commit 기록, Branch, `.git` 정보도 함께 가져온다.

| `git clone` | `git pull` |
|---|---|
| 저장소를 처음 복제 | 기존 저장소를 최신 상태로 갱신 |
| 새 폴더 생성 | 현재 프로젝트 업데이트 |
| 보통 처음 한 번 사용 | 이후 반복 사용 |

---

## 18. Push와 Pull

### 로컬 → 원격

```bash
git push origin main
```

처음 연결할 때:

```bash
git push -u origin main
```

이후에는 다음처럼 사용할 수 있다.

```bash
git push
```

### 원격 → 로컬

```bash
git pull origin main
```

`git pull`은 원격 변경 내용을 가져와 현재 브랜치에 통합한다.

# 💡 오늘 이해한 내용

Git은 파일을 수정한 뒤 바로 기록하는 것이 아니라, **Working Directory → Staging Area → Repository**의 과정을 거친다.

`reset`은 기존 Commit History를 변경할 수 있고, `revert`는 이력을 유지한 채 취소 Commit을 만든다.

`merge`는 두 브랜치의 작업을 통합하고, `rebase`는 내 Commit을 새로운 기준 위에 다시 적용한다.

`git clone`은 원격 저장소를 내 컴퓨터에 처음 복제하는 명령어이며, 이후에는 `pull`과 `push`로 변경 사항을 주고받는다.
